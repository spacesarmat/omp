# Монитор парсеров

Workflow `.github/workflows/parser-monitor.yml` раз в 12 часов (cron `17 */12 * * *`, то есть 00:17 и 12:17 UTC)
запускает **настоящие парсеры приложения** (`src/sources/*`) против живых сайтов с раннера GitHub и сообщает
администратору, когда сайт трекера изменился и парсер сломался.

## Что проверяется

Все встроенные парсеры сайтов из `src/sources/builtin.ts`: Rutor, NNM-Club, Anidub, BigFANGroup, torrent.by,
RuTracker, Kinozal, Rustorka. Jackett/Prowlarr и поиск самого TorrServer — не парсеры сайтов, их нет. Новый парсер,
добавленный в `builtin.ts` без записи в `scripts/parser-monitor/probes.ts`, роняет запуск — так его не забудут.

Для каждого источника:

- 2–3 фиксированных запроса («Джентльмены», «Interstellar», «Во все тяжкие»; для Anidub — «Наруто», «Атака титанов»);
- не меньше N результатов (порог свой у каждого источника);
- у ≥ 90 % результатов есть название, размер, сиды (число), магнет или ссылка на .torrent/страницу раздачи, категория
  (где сайт её даёт); хотя бы у одного результата сиды > 0;
- для одного результата — путь, которым приложение добавляет раздачу: магнет со страницы раздачи (NNM-Club,
  RuTracker), скачивание .torrent (Anidub, BigFANGroup), `resolve` (Kinozal, Rustorka), магнет в списке (Rutor,
  torrent.by).

Сайты со входом (RuTracker, Kinozal, Rustorka) проверяются со входом, только если в репозитории есть секреты (ниже).
Без них — то, что работает без входа: страница поиска (для Kinozal и Rustorka она разбирается их парсером) и форма
входа с теми полями, что отправляет приложение. Такой результат — «⚠️ только без входа».

## Итоги

| Итог | Значит |
|---|---|
| ✅ OK | парсер работает |
| ❌ BROKEN | сайт отвечает (HTTP 200), а парсер ничего не нашёл / не хватает полей / страница входа без нужных полей — **это поломка парсера** |
| 🚫 BLOCKED | Cloudflare, 403/429/451/5xx, бан IP («введите проверочный код»), таймаут или сеть — сайт не пускает раннер GitHub, **не баг парсера** |
| ⚠️ PARTIAL | проверено только без входа, или поиск работает, а шаг ссылки упёрся в блокировку |

Источник BROKEN, если сломана хотя бы половина запросов (одна странная выдача — не поломка).

## Оповещения

Шум отсекается: оповещение уходит, только когда источник **BROKEN два запуска подряд**.

1. **Issue** «Парсер <источник> сломан» с меткой `parser-monitor` (метку workflow создаёт сам): что упало, запрос,
   HTTP-статус, кусок HTML до 3 КБ там, где парсер искал таблицу (без скриптов; id сессий, скрытые поля и логин
   замаскированы), время. Пока поломка та же — тишина; если ошибка изменилась — комментарий. Когда парсер снова
   работает (OK или PARTIAL) — комментарий и issue закрывается. BLOCKED ничего не открывает и не закрывает.
2. **Telegram** в личку администратору: при новой поломке и при восстановлении, коротко, со ссылкой на issue.
3. **Сводка раз в неделю** в Telegram: первый запуск между понедельником 06:00 и вторником 06:00 UTC — по
   расписанию это понедельник 12:17 UTC, ближайший к 09:00. Пример:
   `Парсеры: ✅ Rutor, ✅ NNM-Club, ⚠️ RuTracker (только без входа), 🚫 torrent.by (блокирует GitHub)`.

Состояние между запусками — `parser-monitor.json` в отдельной ветке **`monitor-state`** (создаётся при первом
запуске; ветку `gh-pages` с лентами обновлений монитор не трогает).

## Секреты и переменные

Ничего обязательного: без секретов входа монитор работает, просто сайты со входом будут «только без входа».

| Имя | Вид | Зачем |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | secret (уже есть, его использует release.yml) | бот, который пишет администратору; без него Telegram пропускается |
| `MONITOR_TG_CHAT` | variable, необязательная | чат для сообщений; по умолчанию `536445442` (личка администратора, записан в workflow — id чата не секрет) |
| `RUTRACKER_LOGIN`, `RUTRACKER_PASSWORD` | secrets, необязательные | проверка RuTracker со входом |
| `KINOZAL_LOGIN`, `KINOZAL_PASSWORD` | secrets, необязательные | проверка Kinozal со входом |
| `RUSTORKA_LOGIN`, `RUSTORKA_PASSWORD` | secrets, необязательные | проверка Rustorka со входом |

Бот должен уже переписываться с администратором (иначе Telegram не даст ему написать первым). Для входа лучше
завести отдельные учётки: логин маскируется в issue, но сайт может сбросить сессию, если с ней ходят с разных IP.
Если сайт отказал во входе (капча, неверный пароль) — итог «⚠️ только без входа», в отчёте `login: failed`.

## Запуск вручную

- На GitHub: Actions → **Parser monitor** → Run workflow. Флажки: `summary` — прислать недельную сводку сейчас,
  `dry_run` — только проверить (без issue, Telegram и сохранения состояния), `sources` — только эти источники
  (`rutor,anidub`), `notify` — когда запуск закончится, прислать его таблицу администратору в Telegram (даже если
  проверка упала — тогда «❌ не дошла до конца» со ссылкой).
- Из Telegram: админ-бот (`ops/admin-bot/`), команда `/check` или `/check rutor` — запускает этот workflow с
  `notify=true`; таблицу присылает сам workflow (шаг «Report to the admin», `scripts/parser-monitor/notify.mjs`):
  Cloudflare Worker не может ждать 5–40 минут запуска. `/status` показывает последнюю сохранённую таблицу.
- Локально: `npm run monitor:parsers` (сеть нужна, issue и Telegram не трогает). Переменные окружения:
  `MONITOR_SOURCES=rutor,anidub`, логины из таблицы выше, `MONITOR_OUT` — папка вывода.

Обычный `npm test` в сеть не ходит: живые проверки — отдельный конфиг `vitest.monitor.config.ts`. Логика
классификации, состояния и оповещений покрыта тестами `tests/parserMonitor/`.

## Как читать результат

- **Job summary** запуска — таблица источников с итогом.
- **Артефакт `parser-monitor`** (14 дней): `report.json` — все проверки (запрос, HTTP, сколько результатов, чего не
  хватило, кусок HTML), `actions.json` — какие оповещения решено отправить, `parser-monitor.json` — новое состояние.
- **Issue** с меткой `parser-monitor` — открытые поломки. Чинится парсер в `src/sources/<источник>.ts`; кусок HTML
  в issue показывает, как сейчас выглядит страница. После исправления issue закроется сам на ближайшем запуске
  (или запустите workflow вручную).
- BLOCKED с раннеров GitHub — обычное дело для сайтов за Cloudflare (RuTracker, Kinozal, Rustorka, NNM-Club) и для
  torrent.by с его баном IP: это не поломка, у пользователей на телефоне те же сайты могут работать.

## torrent.by и TLS

torrent.by отдаёт только свой сертификат, без промежуточного Let's Encrypt YE1. Браузер дотягивает его сам (AIA),
Node — нет, поэтому на раннере каждый запрос падал с `UNABLE_TO_VERIFY_LEAF_SIGNATURE` и до парсера дело не доходило.
Теперь для torrent.by (и только для него) монитор доверяет тем же промежуточным YE1–YE3, что лежат в Android-приложении
(`android/app/src/main/res/raw/letsencrypt_ye.crt`, см. `network_security_config.xml`): `scripts/parser-monitor/tlsFetch.mjs`
ходит туда через `node:https` с `ca` = корни Node + этот файл и `allowPartialTrustChain` (их корня ISRG Root YE
в Node пока нет). Сертификат сайта по-прежнему проверяется полностью: подпись, имя, срок. `NODE_EXTRA_CA_CERTS` не
подходит: он доверяет файлу для всех сайтов и не разрешает неполную цепочку. Остальные сайты — обычный `fetch`.
Если torrent.by когда-нибудь сменит промежуточный сертификат на не-YE, обновить файл в `res/raw` (он общий).

Код: `scripts/parser-monitor/` — `logic.ts` (чистая логика), `probes.ts` (проверки источников), `nodeHttp.ts`
(http для Node: куки, перенаправления, windows-1251), `tlsFetch.mjs` (цепочка torrent.by), `run.live.ts` (запуск),
`alerts.mjs` (issue и Telegram), `notify.mjs` + `telegramTable.mjs` (таблица в Telegram по `notify`).
