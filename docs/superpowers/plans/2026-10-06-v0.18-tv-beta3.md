# OMP 0.18.0-beta.3 (ТВ ищет раздачи через телефон) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the LG TV searches torrent sites through the paired phone. The phone always answers, even with OMP closed: a foreground service runs a small HTTP RPC server and a hidden page with the shared source code. The TV gets a new search screen (mockup 6) and, on LG, a «Источники поиска» screen for the phone's sites (mockup 7). Without a reachable phone, the LG falls back to TorrServer (Rutor, Jackett) and says so.

**Architecture:**
- **Phone (Android).** `PhoneRpcService` is a foreground service of type `specialUse` with a quiet, persistent notification «OMP: поиск для телевизора». It owns:
  - a `ControlServer` on a persistent port (SharedPreferences);
  - an `RpcRoute`, which checks the token in the path, LAN-only client IPs and body caps;
  - an `RpcPageHost`, a long-lived hidden WebView like `MonitorHost` that loads `rpc.html`.
  - Each HTTP request is forwarded to the page over the WebMessage bridge (id-correlated, 4.5 s wait). The page runs `searchAll` / `resolveLink` with the app's own `SourceServices` (same cookies and secrets as the app), the same way the monitor page does.
- **Address handover.** The phone sends `{url, token, name}` to the TV as a `phone` launch param on every `launchOnTv`, which also covers the LG attach. The TV stores it persistently (`tsp.phoneLink`).
- **TV.** `phoneRpc()` is an XHR text/plain POST to `/omp/<token>/rpc` with a 5 s timeout. A phone search is wrapped in the same handle interface as a TorrServer `searchAll`, so the search screen does not care who searches. When the RPC fails, the TV falls back to TorrServer with «Телефон не отвечает — откройте OMP на телефоне».

**Tech Stack:** Kotlin (Android Service, WebView + androidx.webkit WebMessageListener, JUnit), Preact + @preact/signals + norigin spatial navigation (TV, Chromium 53), Preact (phone), vitest + jsdom, TypeScript.

**User decisions that supersede the spec text:**
- The phone answers ALWAYS: a foreground service with a quiet persistent notification, not «пока работает приложение или MonitorHost».
- A switch in the phone Settings controls it. It is on by default once a TV is saved, and it can be turned off.
- A `resolve` RPC method is added for results without a magnet (rutracker, nnm, kinozal).
- The TV stores `{url, token, name}` persistently.
- Task 8 brings the spec section in line with these decisions.

**Security decision (justified):** any client whose IP is in a private LAN range (IPv4 10/8, 172.16/12, 192.168/16, 169.254/16; IPv6 link-local / ULA fc00::/7) may call, if it has the token. The server does **not** accept only the paired TV's IP, for three reasons:
- When OMP is closed, the phone does not know the TV's current IP. A DHCP lease change would silently break search until the user opens OMP again.
- One phone may serve several TVs (the saved TV list).
- The token is the real credential. It has 128 bits, is compared in constant time, and travels only in the launch param over the TV's own SSAP channel.

Public, CGNAT (100.64/10) and loopback addresses are refused before the body is read, so the server never answers on mobile data. Turning the Settings switch off stops the service and deletes the token. Turning it on again creates a new token, which revokes every TV. Responses never contain cookies, passwords, `Link` URLs or `detailUrl`s.

```kotlin
package com.spacesarmat.omp.rpc

interface RpcPrefs { fun getInt(k: String): Int?; fun getString(k: String): String?; fun getBool(k: String): Boolean?
                     fun put(k: String, v: Any?) }            // null removes; SharedPreferences adapter in Task 2
class RpcConfig(private val prefs: RpcPrefs, private val random: java.security.SecureRandom = java.security.SecureRandom()) {
    companion object { const val PREFERRED_PORT = 8097; val TOKEN = Regex("^[0-9a-f]{32}$") }
    val enabled: Boolean                      // false when never set (JS decides the default, Task 4)
    fun setEnabled(on: Boolean)               // off: also removes the token (revokes every TV)
    fun token(): String                       // stored one, or a new 32-hex token saved at once
    fun port(): Int                           // stored one, or PREFERRED_PORT
    fun savePort(p: Int)                      // after a bind fell back to an OS-chosen port
}
object LanAddress { fun allowed(a: java.net.InetAddress?): Boolean }   // private v4 / link-local / ULA; not loopback, not 100.64/10

sealed class RpcOutcome { data class Ok(val resultJson: String) : RpcOutcome()
                          data class Failed(val code: String, val message: String?) : RpcOutcome() }
class RpcDispatcher(private val send: (String) -> Boolean, private val waitMs: Long = 4_500) {
    fun call(method: String, params: org.json.JSONObject): RpcOutcome   // blocks the worker thread
    fun onReply(rpc: Int, ok: Boolean, result: Any?, code: String?, message: String?)
    fun failAll(code: String)                                          // page gone: every waiter gets Failed(code)
}
class RpcRoute(private val token: () -> String, private val dispatcher: () -> RpcDispatcher?,
               private val allowed: (java.net.InetAddress?) -> Boolean = LanAddress::allowed) {
    companion object { val METHODS = setOf("sources", "search", "searchPoll", "searchCancel", "setSourceEnabled", "resolve")
                       const val MAX_RESPONSE = 1_000_000 }
    fun precheck(head: com.spacesarmat.omp.control.ControlHead): com.spacesarmat.omp.control.ControlResponse?
    fun route(req: com.spacesarmat.omp.control.ControlRequest): com.spacesarmat.omp.control.ControlResponse
    fun cors(origin: String?): String? = "*"
}
```

`RpcDispatcher.send(json)` posts `{"rpc":n,"method":m,"params":{…}}` to the page and returns false when no page is attached. That immediately gives `Failed("not_ready")`. A missing reply within `waitMs` gives `Failed("timeout")`, and a late reply is dropped. At most 8 calls can wait at once; a ninth gives `Failed("not_ready")`.

`RpcRoute.precheck` answers before the body is read:
- 404 `{}` when `!LanAddress.allowed(head.remote)`.
- 404 `{}` when the path is not exactly `/omp/<token>/rpc`, compared with `MessageDigest.isEqual`.
- 405 for a method other than POST (OPTIONS is answered by `ControlServer` with 204).
- 413 when the length is over `ControlServer.MAX_BODY`.

`route` parses `{method, params}`:
- A malformed body gives `bad_request`, and a method outside `METHODS` gives `unknown_method`.
- Otherwise it calls the dispatcher and wraps the outcome as `{"ok":true,"result":…}` or `{"ok":false,"error":{"code","message"}}`, always with HTTP 200.
- An answer longer than `MAX_RESPONSE` becomes `{"ok":false,"error":{"code":"failed"}}`.

```kotlin
sealed class RpcPageMessage {
    object Ready : RpcPageMessage()                                       // {op:'ready'}: the page is listening
    data class Reply(val rpc: Int, val ok: Boolean, val result: Any?, val code: String?, val message: String?) : RpcPageMessage()
    data class Bridge(val request: com.spacesarmat.omp.monitor.BridgeRequest) : RpcPageMessage()   // only Http / SecretGet
    data class Invalid(val id: Int?, val error: String) : RpcPageMessage()
}
object RpcProtocol {
    const val MAX_MESSAGE = 1_000_000
    fun parse(text: String?): RpcPageMessage            // {op:'rpcReply', rpc, ok, result | error:{code,message}}
    fun request(rpc: Int, method: String, params: org.json.JSONObject): String
}
```

The bridge flow:
1. The page sends `{op:'ready'}` once.
2. `RpcPageHost` keeps that message's `JavaScriptReplyProxy` as the push channel. The dispatcher's `send` posts `RpcProtocol.request(...)` through it on the main thread and returns false while there is no proxy.
3. The page answers with `{op:'rpcReply', ...}`, which goes to `dispatcher.onReply`.
4. `http` / `secretGet` work exactly like `MonitorHost` (`services.request(spec)`, `services.secrets.get`). Every other monitor op (`start`, `notify`, `persist`, `finish`) is `Invalid`.

JS-facing plugin API (`mobile/src/platform/native.ts`):

```ts

rpcInfo(): Promise<RpcInfo | null>;                    // null off-device or when disabled
```

`name` is `Build.MANUFACTURER` capitalised + " " + `Build.MODEL`, for example «Samsung SM-G998B», at most 60 chars. `ip` is `LocalTorrServer.wifiIpv4(ctx)`, or null when the phone has no Wi-Fi.

Service behaviour:
- `onStartCommand`: `I18n.load(this)`, then start foreground. A failure is caught as in `TorrServerService`: `stopSelf`, `START_NOT_STICKY`.
- Notification:
  - Channel `omp-rpc`, importance `IMPORTANCE_MIN`, no sound, no badge.
  - Ongoing, title `rpc.title` «OMP: поиск для телевизора», text `rpc.text` «Телевизор ищет раздачи через этот телефон».
  - Tapping it opens `MainActivity`.
- Server: `ControlServer(config.port(), route::precheck, route::route, route::cors).start()`. On a `BindException`, the service retries with port 0 and calls `config.savePort(server.localPort)`.
- Page: create the `RpcPageHost` on the main thread. If the page is gone (`onRenderProcessGone`), `failAll("not_ready")` and recreate it after 2 s, at most 3 times per 10 min.
- `onDestroy`: stop the server, `failAll`, destroy the WebView.
- No wake lock and no Wi-Fi lock in this beta (see «Open decision» below).

Method behaviour:
- **`sources {}`** → `{sources: RpcSource[]}`.
  - Calls `reloadSourcePrefs()` first.
  - Lists only `kind !== 'torrserver'` (builtins + indexers); the TV has its own TorrServer.
  - State follows `mobile/src/screens/Sources.tsx` L483-513:
    - `!on` → `off`.
    - `needsLogin && loggedIn() === false` → `login`.
    - A health error with `isCloudflare(message)` → `cloudflare`.
    - Any other health error → `error` (with `message`).
    - `loggedIn() === true` and no health → `loggedIn`.
    - Health ok → `ok`.
    - Nothing known → `unknown`.
  - The `loggedIn` checks run in parallel, and any not finished after `SOURCES_WAIT_MS` count as unknown.
- **`search {query, sources?}`** → `{handle: string, sourceIds: string[]}`.
  - `query` is trimmed, 1–200 chars, else `bad_request`. `reloadSourcePrefs()` runs first.
  - The sources are `sources` ∩ enabled non-torrserver sources, or all enabled non-torrserver sources.
  - The handle id is 16 random hex chars. A 4th live handle cancels and drops the oldest.
  - Every `onResult` / `onDone` increments `rev`.
- **`searchPoll {handle, rev?}`** → `RpcPoll`.
  - `results` is present only when `rev` differs from the one sent. It is `sortResults(h.results(), 'seeds').slice(0, MAX_RESULTS)` mapped to `RpcResult`, with `key = resultKey(r)`.
  - `failed` comes from `getHealth(id)`: `message` and `code`, with `'cloudflare'` when `isCloudflare(message)`.
  - An unknown or expired handle gives `expired`.
- **`searchCancel {handle}`** → `{}`. It cancels and drops the handle; an unknown handle is fine.
- **`setSourceEnabled {id, on}`** → `{on}`. An unknown id, a torrserver-kind id or a non-boolean `on` gives `bad_request`.
- **`resolve {handle, key}`** → `{link}` or `{pending: true}`.
  - Only rows this phone found in that live handle can be resolved, so the TV cannot make the phone fetch arbitrary URLs.
  - The first call starts `resolveLink(row, ctx)` and caches the promise per `handle:key`. The call waits at most `RESOLVE_WAIT_MS`; if it is not done, it answers `{pending: true}`. Later calls return the cached result.
  - A rejection gives `failed` with the message. An unknown handle gives `expired`, and an unknown key gives `bad_request`.
- Handles not touched for `HANDLE_TTL_MS` are dropped by a 60 s sweep.

`startTvSearch`:
- No `phoneLink` → `{torrServerSearch(q), 'noPhone'}`.
- Otherwise it tries `phoneSearch(q)`; on any `PhoneRpcError` → `{torrServerSearch(q), 'phoneDown'}`.

`phoneSearch`:
- Polls `searchPoll {handle, rev}` every `POLL_MS` until `done`, and keeps the last `results` (mapped with `via`).
- Two consecutive poll failures mark the phone sources as failed. It then starts `torrServerSearch` and continues as a combined handle (rows of both, `by` stays `'phone'`, and `failures()` gains `{id:'phone', message:''}`). `done` resolves when both are done.

- A poll that answers `expired` ends the search with the rows so far.
