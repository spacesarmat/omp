# OMP Theme and Interaction Editor Design

## 1. Назначение

OMP нужен локальный редактор оформления и поведения, который позволяет Andy без ручного редактирования исходников:

- выбирать реальный экран и его состояние;
- менять оформление визуально и сразу видеть результат;
- назначать независимый внешний вид Windows, macOS и Linux при одинаковых функциях;
- редактировать темы телефона, Android TV и LG webOS;
- проверять вертикальный и горизонтальный формат, размеры окна и ТВ-разрешения;
- задавать переходы между экранами и разрешённые действия через правила;
- проверять сценарии на тестовых данных без реальных устройств и серверов;
- сохранять черновики, сравнивать версии и привязывать результат к будущему релизу;
- экспортировать изменения в отдельную ветку и PR без прямого изменения `main`.

Это крупный самостоятельный проект, а не одно изменение CSS. Реализация разделяется на небольшие PR, но конечная архитектура должна сразу поддерживать все перечисленные цели.

## 2. Решения Andy

- Выбран вариант 1: общие desktop-экраны и навигация, независимые темы для каждой desktop ОС.
- Windows, macOS и Linux имеют одинаковые функции, но собственный внешний вид.
- Изменение темы Windows не меняет автоматически macOS, Linux или телефон.
- Редактор должен поддерживать не только стили, но и логику переходов и действий.
- Для телефона нужны вертикальный и горизонтальный форматы.
- Результат можно привязывать к платформе и будущему релизу.

## 3. Текущее состояние проекта

- `mobile/src` содержит экраны телефона. `desktop/src/main.tsx` сейчас импортирует `mobile/src/main`, поэтому Windows использует телефонный UI через адаптер `desktop/src/platform/native.ts`.
- `src` содержит отдельный ТВ-интерфейс для LG webOS и Android TV. Он не должен быть объединён с desktop UI.
- `mobile/src/mobile.css` и `src/styles.css` уже используют CSS custom properties, но имена и покрытие переменными различаются. Например, встречаются `--panel-2` и `--panel2`.
- Ориентация телефона зависит от CSS и вычислений в `mobile/src/ui/landscapeCols.ts`. Для предпросмотра недостаточно повернуть картинку: нужен реальный viewport нужного размера и события resize.
- ТВ-интерфейс использует логический размер 1920x1080. Проверки 720p, 1080p и 4K должны использовать существующие правила масштабирования.
- `src/testmode/registry.ts` содержит стабильные коды ТВ и телефонных экранов. Существующие коды нельзя перенумеровывать.
- `scripts/screenshots.mjs` использует статические сцены для документации. Редактору нужны настоящие приложения с тестовыми данными, а не эти статические HTML-макеты.
- Windows уже имеет независимую версию desktop пакета. macOS и Linux проходят базовую CI-матрицу, но готовых пакетов для них пока нет.

## 4. Цели

1. Редактировать настоящие компоненты OMP, а не отдельную упрощённую копию интерфейса.
2. Разделить телефонный и desktop UI, сохранив общие данные, API и бизнес-логику.
3. Использовать одну реализацию desktop-экранов для Windows, macOS и Linux с независимыми темами.
4. Поддерживать постепенное подключение экранов телефона и ТВ без одномоментного переписывания проекта.
5. Дать безопасный декларативный редактор поведения с готовыми событиями, условиями и действиями.
6. Показывать влияние изменения на другие платформы до сохранения.
7. Получать воспроизводимые, читаемые и проверяемые изменения в Git.
8. Не допускать выполнения реальных действий из предпросмотра.

## 5. Не входит в первую версию

- Произвольный JavaScript, загрузка скриптов и выполнение команд операционной системы из документов темы или правил.
- Публичный каталог тем, магазин, аккаунты авторов и сетевая синхронизация черновиков.
- Автоматическая установка тем пользователями поверх выпущенного приложения.
- Полный no-code конструктор бизнес-логики и новых сетевых протоколов.
- Автоматическое создание стабильного релиза, merge в `main`, deploy на NUC или действия на устройствах.
- Редактирование нативного интерфейса 2160 Player.
- Одновременный перенос всех экранов в новую архитектуру в одном PR.
- Обязательные готовые установщики macOS и Linux как условие начала работы над их темами.

Это ограничения первой версии редактора, а не запрет на будущее развитие.

## 6. Анти-цели

- Отдельный визуальный редактор, результат которого невозможно воспроизвести в реальном приложении.
- Три копии desktop-бизнес-логики или три независимых набора одинаковых экранов.
- Незаметное изменение телефона при редактировании Windows.
- Генерация больших нечитаемых файлов, которые нельзя проверить в PR.
- Произвольное выполнение кода или доступ редактора к секретам, production и реальным платежам.
- Обязательная миграция всего приложения на новые современные CSS-функции, которые не поддерживает ТВ.

## 7. Рассмотренные подходы

### Выбран: общие desktop-экраны и независимые темы ОС

Desktop-навигация, компоненты и функции общие. Тема определяет внешний вид каждой ОС через токены и разрешённые переопределения. Редактор логики добавляется отдельным декларативным слоем и не превращает темы в скрипты.

Преимущество: одинаковые функции не дублируются, а внешний вид можно менять независимо. Ограничение: структура desktop-экранов общая, хотя размеры, компоновка и стили допускают платформенные варианты.

### Отклонён: отдельные экраны для каждой desktop ОС

Даёт максимальную свободу, но утраивает UI-код, тесты и стоимость каждой новой функции. Для требования одинаковых функций это избыточно.

### Отклонён: полный JSON-конструктор всех экранов

Позволяет описывать почти любой UI, но требует отдельного языка экранов, сложной совместимости и фактически заменяет Preact-фреймворк новым фреймворком. JSON используется только для тем, ограниченных переопределений и правил, а не для описания всего приложения.

## 8. Целевые платформы и экраны

Идентификаторы целей редактора:

- `android-phone`;
- `android-tv`;
- `lg-webos`;
- `desktop-windows`;
- `desktop-macos`;
- `desktop-linux`.

Для каждой цели редактор показывает список поддерживаемых экранов и уровень поддержки:

- `preview`: доступен только предпросмотр;
- `theme`: доступно редактирование оформления;
- `logic`: доступны предпросмотр, тема и правила.

Отсутствующий уровень нельзя скрывать: редактор честно показывает, что экран ещё не перенесён. Старые экраны продолжают работать без новых документов.

Для desktop добавляется собственный стабильный реестр идентификаторов экранов и элементов. Существующие коды телефона и ТВ не меняются. Префикс новых кодов выбирает реализатор без конфликтов с текущим реестром.

## 9. Архитектура

### 9.1. Редактор

Новый `editor/` содержит локальное Preact + TypeScript + Vite-приложение и Node-сервис для локальных файловых операций. Используются уже существующие в проекте технологии; новые библиотеки добавляются только при отдельной необходимости.

Редактор не включается в production-бандлы OMP. Он запускается явной командой разработки и по умолчанию доступен только на loopback.

Основные части:

- панель целей, экранов и состояний;
- область реального предпросмотра;
- вкладки `Дизайн`, `Логика`, `Проверка`;
- карта экранов и переходов;
- журнал симуляции;
- история черновиков и сравнение версий;
- панель проверок и экспорта.

### 9.2. Общие документы дизайна

Новый `design/` содержит версионированные документы, которые можно рецензировать в PR:

- семантические токены;
- темы и переопределения целей;
- экранные и ориентационные варианты;
- декларативные правила поведения;
- тестовые сценарии и ссылки на fixtures;
- метаданные базового коммита и предполагаемого релиза.

JSON является исходным представлением документов редактора. Приложения импортируют проверенные локальные документы при сборке. Они не скачивают правила из сети.

Стабильный генератор создаёт CSS из токенов и переопределений. Форматирование и порядок ключей детерминированы, чтобы повторный экспорт без изменений не создавал diff.

### 9.3. Desktop UI

Desktop получает собственные Preact-экраны и навигацию вместо импорта телефонного `mobile/src/main`.

Andy выбрал общий каркас с левым боковым меню. Основные разделы меню: Каталог, Новое, Поиск, Пульт и Настройки. Справа находится область контента и вложенных экранов. На узком окне меню сворачивается до значков без изменения маршрутов и доступных функций.

Структура навигации общая для Windows, macOS и Linux. Тема может менять ширину меню, цвета, шрифты, значки, отступы и оформление выбранного пункта, но не меняет независимо состав обязательных функций. Пункты меню и их действия редактируются через тот же реестр разрешённых правил, что и остальные элементы. Нижнее телефонное меню в desktop shell не используется.

Общими остаются:

- stores и состояние;
- каталог, поиск, библиотека и источники;
- billing и deep links;
- работа с TorrServer;
- запуск и состояние плеера;
- настройки, история и локальные данные;
- TypeScript и Rust platform bridges.

Не переносятся механически из телефона:

- нижняя телефонная навигация;
- телефонные жесты как единственный способ управления;
- телефонные safe-area предположения;
- стили, рассчитанные только на узкий экран.

Миграция выполняется по экранам. Пока desktop-экран не перенесён, существующая реализация остаётся рабочей, а редактор не заявляет поддержку нового уровня для этого экрана.

Новый desktop shell содержит единый реестр логических маршрутов. Каждый маршрут указывает либо на новый desktop-компонент, либо на адаптер существующего телефонного экрана. Реестр не импортирует телефонный `App` целиком и не показывает телефонный `NavBar` внутри desktop shell.

Навигация и история общие для обеих реализаций. Адаптер переводит существующий `MRoute` в логический desktop route и сохраняет параметры, back stack и deep links. Миграция экрана заменяет компонент в реестре без изменения идентификатора маршрута и бизнес-операций.

Legacy-экран работает в собственной области с прежними стилями. Desktop-тема применяется к нему только после явной миграции его токенов. Это исключает частичное смешение телефонного и desktop оформления.

### 9.4. Телефон и ТВ

Существующие приложения не переписываются ради редактора. Для них добавляются адаптеры к токенам, предпросмотру и разрешённым правилам.

ТВ экспортирует только совместимый CSS. Container style queries, `:has()` и другие новые механизмы не используются как обязательная основа. Для тем применяются custom properties, классы и селекторы с предсказуемым приоритетом. Существующие запреты flex `gap`, `aspect-ratio`, `inset` и `:has()` сохраняются.

### 9.5. Сборка тем и существующий CSS

Исходные JSON-документы и сгенерированные CSS-файлы коммитятся. Приложения импортируют готовый CSS своей цели после существующего CSS. CI повторно запускает генератор и требует отсутствия diff, поэтому устаревший или вручную изменённый generated-файл не проходит проверку.

Генератор не пытается переопределить произвольный старый селектор повышением specificity или массовым `!important`. При миграции редактируемое объявление сначала переводится на семантическую CSS-переменную с прежним значением как fallback. После этого генератор устанавливает переменные в явных областях цели, экрана, формата, состояния или зарегистрированного элемента.

Области используют data-атрибуты и документированный порядок CSS. Приоритет не зависит от случайной глубины старых селекторов. Для ТВ не применяются `@layer` и `:where()` как обязательная основа, поскольку старый браузер их не поддерживает.

Немигрированные объявления остаются в существующем CSS с прежним результатом. Миграция одного свойства не требует перевода всего файла на новую каскадную систему.

## 10. Модель темы

Каждый документ содержит как минимум:

- `schemaVersion`;
- стабильный `id` и название;
- `baseCommit`;
- целевые платформы;
- `releaseIntent`, если выбран будущий релиз;
- общие семантические токены;
- переопределения платформ, экранов, форматов и состояний;
- метаданные ревизии.

Токены делятся на уровни:

1. Базовые значения: палитра, шрифты, размеры, отступы, радиусы.
2. Семантические значения: фон, панель, текст, muted, accent, danger, focus.
3. Компонентные значения: кнопка, карточка, поле, меню, панель навигации.

Не требуется переводить весь CSS на четыре уровня токенов. Новые уровни добавляются только там, где они нужны редактору.

Порядок наследования:

```text
Общая тема -> Платформа -> Компонент -> Экран -> Элемент -> Формат -> Состояние
```

Более поздний уровень имеет приоритет. Редактор показывает итоговое значение, источник и цепочку наследования каждого свойства. Можно сбросить только переопределение текущего уровня, не удаляя базовую тему.

Нажатие на элемент по умолчанию показывает связанный компонент и семантические токены. Изменение общего токена предлагается до создания отдельного исключения.

Элементное переопределение разрешено только для элемента со стабильным `data-design-id` и только для свойств из явного allowlist: цветов, типографики, отступов, размеров, границ, радиусов, выравнивания и разрешённых параметров компоновки. Нельзя задавать произвольный селектор, CSS-текст, HTML или JavaScript. Скрытие обязательной функции через `display` или `visibility` не входит в allowlist.

`data-design-id` назначается в компоненте, а не вычисляется по порядку DOM-элементов. При повторяющихся карточках переопределение относится к типу элемента, а не к случайному номеру строки. Переопределение конкретной записи данных возможно только через отдельный явный fixture и не попадает в общую тему.

Если элемент ещё не зарегистрирован, редактор подсвечивает ближайший зарегистрированный компонент и сообщает об ограничении. Он не создает хрупкий селектор вроде `nth-child` автоматически.

Для текущих несовпадающих имён вроде `--panel2` и `--panel-2` вводится семантическое имя с временными legacy-alias. Старые имена удаляются только после миграции использований.

## 11. Модель логики

### 11.1. Правило

Правило имеет вид:

```text
Событие -> Условия -> Действие
```

Каждое правило содержит стабильный `id`, область действия, событие, необязательные условия, действие и параметры. Порядок правил явный. Конфликты двух включённых правил на одно событие показываются до экспорта.

Поддерживаются составные условия `all`, `any` и `not`. Циклы выполнения действий внутри одного события запрещены. Переходы между экранами по действию пользователя не считаются ошибочным циклом сами по себе.

### 11.2. События

Первая версия реестра предусматривает:

- click, double click и long press;
- hover и focus;
- клавиши клавиатуры и пульта;
- swipe там, где поддерживает платформа;
- открытие и закрытие экрана;
- изменение указанной настройки;
- success и error разрешённого асинхронного действия;
- завершение загрузки или воспроизведения.

Конкретный экран получает только события, которые поддерживают его элементы и платформа.

### 11.3. Действия

Реестр действий типизирован и ограничен:

- navigate, back, close screen;
- open или close sheet, dialog, menu;
- switch tab, filter, theme;
- set разрешённого UI-state;
- start search с типизированными параметрами;
- select title, torrent, season или episode;
- play, pause, stop через существующий player API;
- open server settings или connect flow;
- show toast или error;
- вызов явно зарегистрированной native capability.

Действие нельзя задать произвольной строкой кода. Параметры проверяются схемой. Доступность действия зависит от платформы, экрана и текущего состояния.

Новая бизнес-операция сначала реализуется обычным кодом, получает тесты и затем регистрируется как доступное действие редактора.

### 11.4. Общие и платформенные правила

Логика общая по умолчанию. Платформенное переопределение допускается для ввода и системных возможностей. Например, карточка везде открывает один и тот же фильм, но долгое нажатие телефона, правый клик Windows и кнопка меню пульта могут вызывать разные UI-действия.

Переопределение не должно незаметно менять функциональный результат desktop ОС. Редактор предупреждает о расхождении основных сценариев Windows, macOS и Linux.

### 11.5. Выполнение правил в приложении

Небольшой ограниченный rule interpreter входит в production-бандл только вместе с подключёнными правилами. Он импортирует локальные проверенные JSON-документы, но не содержит `eval`, загрузку сетевых правил или выполнение произвольных функций. Один и тот же интерпретатор используется в симуляторе и приложении, поэтому поведение предпросмотра не требует отдельной реализации.

Генерация TSX-обработчиков из JSON не используется: она создавала бы хрупкий второй компилятор компонентов. Генерируется только CSS, а правила остаются типизированными данными с проверкой схемы при сборке.

Подключение правил выполняется поэлементно. На мигрированном событии элемента есть один владелец: либо существующий императивный обработчик, либо rule dispatcher. Одно событие не выполняет оба пути. Миграция явно заменяет старый обработчик и добавляет регрессионный тест на один dispatch.

На немигрированном экране существующие обработчики остаются единственным источником поведения. В production действия вызывают настоящие зарегистрированные API, а в редакторе те же действия получают только mock-результат.

## 12. Предпросмотр и симулятор

### 12.1. Настоящие приложения

Предпросмотр запускает существующие phone, TV и desktop bundles в изолированных iframe или эквивалентных preview-контейнерах. Preview-адаптер заменяет native bridge тестовой реализацией.

Каждый preview получает:

- цель и идентификатор экрана;
- fixture состояния;
- размер viewport и масштаб обзора;
- язык;
- тему и переопределения;
- разрешённые тестовые ответы API.

В production отсутствуют панель редактора, файловый сервис, mock bridge и загрузка документов из сети. Локальные правила выполняются только для явно мигрированных элементов.

### 12.2. Состояния

Для экрана можно выбрать loading, empty, error, populated, long text и открытый sheet, если такие состояния существуют. Набор состояний задаётся явно fixture и не имитируется случайным изменением DOM.

Обязательны русский и английский предпросмотры. Дополнительные языки используют существующую i18n-систему.

### 12.3. Формат и размер

- Телефон: portrait, landscape, ручной размер, safe-area и изменение сетки через реальные resize-события.
- Desktop: минимальный размер, стандартное окно, максимизированное окно и ручной размер. Понятия portrait и landscape обозначают форму viewport, а не физическую ориентацию ОС.
- ТВ: 1280x720, 1920x1080 и 3840x2160 с существующим логическим масштабом.
- Масштаб панели редактора меняет только обзор и не входит в экспорт.

### 12.4. Безопасная симуляция

Симулятор выполняет правила против тестового состояния и записывает цепочку событий, условий и действий. Он не подключается к реальному TorrServer, биллингу, Telegram, NUC или устройству.

Действия play, download, update, payment и native capabilities возвращают fixture-результат. Для каждого результата можно выбрать success или error.

Журнал показывает:

- исходное событие;
- проверенные условия;
- выбранное правило;
- параметры действия;
- новый экран или состояние;
- ошибку валидации или fixture-ответ.

## 13. Основные сценарии редактора

### Изменение темы

1. Andy выбирает `desktop-windows`, экран и состояние.
2. Нажимает элемент и меняет цвет, шрифт, отступ или размер.
3. Видит результат и источник наследуемого значения.
4. Сравнивает с macOS и Linux либо с предыдущей версией.
5. Сохраняет черновик и запускает проверки.

### Изменение перехода

1. Andy выбирает кнопку и вкладку `Логика`.
2. Выбирает событие `click` и действие `navigate`.
3. Выбирает экран назначения и обязательные параметры.
4. На карте переходов видит новую связь.
5. Проверяет переход и возврат в симуляторе.

### Условное действие

Пример: `Смотреть` открывает плеер при готовом сервере, а иначе открывает connect flow. Правило проверяется в двух состояниях fixture без реального запуска сервера.

### Подготовка релиза

1. Andy выбирает базовый коммит и цель.
2. Указывает версию и канал beta или stable как намерение, не как команду выпуска.
3. Видит изменённые темы, экраны, правила и затронутые платформы.
4. Запускает проверки.
5. Экспортирует в отдельную ветку.
6. После явного подтверждения создаёт PR через существующий GitHub-инструментарий.

## 14. Черновики, история и релизы

Локальные черновики хранятся в `.omp-editor/`, который исключён из Git. Автосохранение не меняет исходники приложения до экспорта.

Экспортированные документы в `design/` версионируются в Git. Черновик содержит `baseCommit`, чтобы редактор мог показать устаревание после изменения `main`.

Поддерживаются:

- undo и redo в текущей сессии;
- сброс свойства, элемента, экрана или темы;
- именованные снимки черновика;
- сравнение двух снимков;
- импорт и экспорт документа с проверкой схемы;
- список затронутых платформ и общих компонентов.

`releaseIntent` включает цель, версию и канал. Он не создаёт тег, GitHub Release, merge, push, Telegram-пост или deploy.

Для macOS и Linux можно готовить темы и предпросмотр до появления пакетов. Привязка к реальному выпуску активируется только после появления соответствующего release workflow.

Все существующие правила репозитория остаются обязательными: отдельный PR, зелёный CI, явное разрешение Andy на merge и отдельная команда на релиз.

## 15. Проверки

### 15.1. Схема и Git

- Строгая валидация JSON и неизвестных полей.
- Проверка `schemaVersion`, стабильных идентификаторов и `baseCommit`.
- Детерминированный экспорт и отсутствие diff при повторном запуске.
- Миграции старых документов тестируются отдельно.
- Нельзя экспортировать изменения за пределы разрешённых каталогов.

### 15.2. Темы

- Контраст текста и видимость фокуса.
- Переполнение, обрезание и длинные строки.
- Минимальные размеры интерактивных элементов.
- ТВ-текст от 24px, кроме существующих тестовых подписей.
- Запрещённые ТВ CSS-конструкции.
- Русский и английский текст.
- Одинаковый визуальный результат ТВ на 1080p и 4K с учётом масштаба.

### 15.3. Логика

- Переход на несуществующий экран.
- Неизвестное событие, условие или действие.
- Отсутствующий обязательный параметр.
- Недоступная платформенная capability.
- Конфликт приоритетов и дублирование идентификаторов.
- Немедленный безусловный цикл действий.
- Экран без входа или без предусмотренного возврата, если он не является корневым.
- Расхождение обязательных desktop-сценариев между ОС.

### 15.4. Регрессионные проверки

- Vitest для схемы, наследования, генератора, правил и компонентов.
- Существующие root, mobile, desktop и billing проверки по затронутой области.
- `cargo test`, если меняется Rust bridge.
- Сборки всех затронутых платформ.
- Скриншоты реальных preview-сценариев, а не только статических макетов.
- Сценарии мыши, клавиатуры, пульта и touch в зависимости от цели.
- Сравнение неизменённого экрана с baseline, чтобы новый слой не менял текущий вид по умолчанию.

Визуальные baseline не обновляются автоматически без просмотра diff. Автоматический accessibility score не заменяет ручную проверку навигации.

## 16. Безопасность

- Node-сервис редактора слушает только `127.0.0.1` и требует случайный токен сессии для изменяющих запросов.
- Проверяются Origin и путь запроса. Сервис не принимает произвольные команды shell.
- Запись разрешена только в `.omp-editor/` и явно перечисленные файлы `design/`.
- Имена веток, файлов и идентификаторов валидируются. Аргументы Git передаются без shell interpolation.
- Редактор не читает `.env`, SSH-ключи, токены, реальные локальные хранилища OMP и пользовательскую историю.
- Fixtures не содержат реальных секретов или платёжных данных.
- Импорт документа ограничен размером и схемой. Документ не содержит исполняемого JavaScript или HTML.
- Iframe preview изолируется от панели редактора. Обмен идёт через типизированный протокол с проверкой origin и источника.
- Push, PR и GitHub-операции выполняются только после отдельного действия Andy и не являются частью автосохранения.

## 17. Совместимость и производительность

- Editor UI может использовать современный Chromium. Экспортируемый код обязан учитывать существующие цели, включая старый ТВ-браузер.
- Не используются новые CSS-функции как обязательная зависимость ядра без подтверждённой поддержки и fallback.
- Предпросмотр загружает только выбранный экран и его fixture. Не все приложения рендерятся одновременно.
- Сравнение платформ запускается по требованию и ограничивает число активных preview.
- Документы темы не добавляют сетевых запросов в production.
- Правила не выполняют произвольные циклы и не создают неограниченные асинхронные цепочки.

## 18. Границы первой поставки и конечный результат

Первый вертикальный срез должен доказать всю цепочку на небольшом наборе экранов:

- локальный редактор;
- реальный desktop preview;
- выбор Windows, macOS и Linux;
- изменение темы одной ОС без изменения других;
- portrait и landscape там, где поддерживает цель;
- одно правило навигации и одно условное действие;
- симуляция без реальных вызовов;
- сохранение черновика;
- валидация и детерминированный экспорт;
- отдельная ветка и проверяемый diff.

Остальные экраны, действия и платформы подключаются последовательными PR. Поддержка редактора не считается завершённой для всего OMP, пока матрица целей и экранов не переведена из `preview` в требуемые уровни `theme` и `logic`.

Конечная проверка: Andy может выбрать экран, изменить внешний вид Windows отдельно от macOS и Linux, задать переход или разрешённое действие, проверить сценарий и получить PR с одинаковыми функциями и независимым оформлением ОС.

## 19. Решения, принятые автором проекта

Это не новые требования Andy, а предлагаемые архитектурные решения, которые он может изменить при утверждении:

- Редактор предназначен только для разработки OMP, не для конечных пользователей.
- Произвольный JavaScript исключён из первой версии. Расширение возможно через зарегистрированные и протестированные действия.
- Локальный Preact/Vite + Node выбран вместо добавления второго desktop-фреймворка.
- JSON описывает темы и ограниченные правила, но не всю структуру Preact-экранов.
- Общая логика используется по умолчанию, платформенные переопределения добавляются явно.
- Миграция выполняется поэкранно с сохранением текущего поведения по умолчанию.
- Desktop shell использует единый реестр маршрутов с адаптерами legacy-экранов на время миграции.
- Элементные стили доступны только для стабильных `data-design-id` и разрешённых CSS-свойств.
- Generated CSS коммитится, а редактируемые свойства постепенно переводятся на переменные вместо борьбы со specificity старого CSS.
- Правила выполняются ограниченным локальным интерпретатором, TSX-обработчики не генерируются.
- Первый PR должен быть небольшим вертикальным срезом, а не попыткой перенести весь UI одновременно.
