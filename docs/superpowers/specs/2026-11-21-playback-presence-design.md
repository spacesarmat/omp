# Playback Presence и UX

Дата: 2026-11-21
Статус: реализация по одобренной realtime-схеме

## 1. Цель

Пользователь на телефоне должен видеть, что сейчас играет на другом устройстве его аккаунта, название, серию, позицию и состояние. Явная кнопка «Продолжить здесь» открывает тот же файл с той же позиции на телефоне. Воспроизведение никогда не перехватывается автоматически.

## 2. Текущее состояние

- `/v1/presence` - install/login аналитика, не playback presence.
- Локальный «Сейчас на ТВ» получает `PlayerState` через прямой пульт телефон-ТВ и без аккаунта billing не показывает состояние других устройств.
- `/v2/sync/ws` уже доставляет committed records, но клиентский V2 еще не подключен.
- Настройки аккаунта уже показывают sync status, список устройств и ручную синхронизацию.

## 3. Подходы

### 3.1. Память процесса, HTTP fallback и WS-сообщения

Выбрано. Playing heartbeat живет только в памяти одного billing-процесса. Текущие клиенты используют HTTP каждые 15 секунд, следующий V2-клиент сможет использовать тот же каталог через WebSocket. Это соответствует spec, не требует ожидания клиентского outbox и не пишет heartbeat в Postgres.

### 3.2. Postgres presence

Отклонено. Запись позиции каждые 15 секунд создает ненужную нагрузку и смешивает ephemeral состояние с durable history.

### 3.3. Только после клиентского V2

Отклонено для этого этапа. Это отложило бы понятный пользовательский результат, хотя HTTP fallback уже является обязательной частью архитектуры.

## 4. Контракт

`PresenceInput` от клиента:

- `state`: `playing`, `paused` или `finished`;
- `sessionId`: непустая строка до 100 символов;
- `sessionSeq`: монотонный положительный safe integer в пределах устройства; новая сессия получает `max(Date.now(), previous + 1)`, сервер отклоняет heartbeat с меньшим seq;
- `hash`: 40 hex символов;
- `fileId`: неотрицательное целое;
- `title` и `episode`: очищенные строки до 180 символов;
- `positionSec` и `durationSec`: конечные неотрицательные числа;
- `deviceName`: до 80 символов;
- `platform`: `lg`, `androidtv`, `phone` или `desktop`.

Сервер добавляет `deviceId` и `updatedAt`, отбрасывает чужие deviceId из body. URL потоков, magnet, токены и серверные пароли в presence запрещены.

- `POST /v2/sync/presence` с `{ presence }` обновляет свое состояние, с `{ presence: null, sessionSeq }` очищает его только если clear не относится к более старой сессии. Ответ: `{ ok, presences, serverTime }`.
- `GET /v2/sync/presence` возвращает `{ ok, presences, serverTime }` без изменения состояния.
- WS `presence { presence }` использует тот же валидатор и рассылает `{ type: 'presence', presences, serverTime }` только устройствам аккаунта.
- Авторизация, подписка, read-only поведение и повторная проверка доступа те же, что у sync V2. GET разрешен в read-only, изменение presence в read-only отклоняется без изменения памяти.

## 5. TTL и жизненный цикл

- Все presence записи имеют TTL 90 секунд. Клиент обновляет открытый плеер каждые 15 секунд и при смене файла, паузе, перемотке и завершении.
- TTL удаляет зависшее устройство. Paused/finished остаются видимыми, пока открытый клиент обновляет их; durable позиция независимо сохраняется существующим progress sync.
- Явный выход из плеера отправляет `presence: null` со своим `sessionSeq`. Clear старой сессии не удаляет новую; clear tombstone блокирует поздний heartbeat той же или более старой сессии, включая heartbeat после clear до первого отчета. Final paused/finished отправляется с новым `sessionSeq`, чтобы опоздавший playing не заменил его. Sequence history сохраняется после TTL видимой строки и автоматически очищается через 24 часа вместе с неактивными account maps. Ошибка сети не мешает локальному воспроизведению.
- Presence живет в памяти процесса и исчезает при его перезапуске. Multi-process broker не входит в этот этап.

## 6. Источники состояния

- LG и Android TV: существующий `buildSnapshot` в `Player.tsx`, без дублирования чтения video element. Название берется из torrent/episode metadata, не из URL.
- Телефон: `watchOnPhone` сообщает начало и результат встроенного 2160 Player. Пока Promise плеера не завершен, keepalive каждые 15 секунд оценивает позицию по прошедшему времени и ограничивает ее известной длительностью; после выхода фактическая позиция заменяет оценку. Промежуточных pause callbacks нет, поэтому точность паузы телефона не обещается. Внешний Android player без callbacks не публикует недостоверное playing presence.
- Desktop reporting и отображение карточек не входят в этот PR и будут подключены вместе с клиентским V2. Для browser desktop требуется отдельно решить CORS или native context.
- Каждый новый playback session получает новые `sessionId` и `sessionSeq`. Поздний heartbeat предыдущей сессии с меньшим seq не заменяет более новую запись того же устройства. Внутри одной сессии допустимы перемотка и last arrival wins.

## 7. UX на телефоне

В блоке аккаунта появляется отдельная карточка для каждого чужого активного presence, отсортированные playing первыми и затем по `updatedAt`:

- «Сейчас играет на LG» или «Пауза на устройстве»;
- название и серия;
- позиция и длительность;
- кнопка «Продолжить здесь».

При одновременной игре на нескольких устройствах пользователь явно выбирает карточку, автоматический выбор и перехват запрещены. Кнопка использует существующий `playOnPhone`, если hash есть в библиотеке и fileId известен. Иначе показывается пояснение без запуска. Собственное устройство скрыто. Опрос работает только на видимом экране настроек. Состояние sync status и ручная синхронизация не меняются.

## 8. Ограничения и откат

- Нет watch party, синхронизации кадр в кадр, автоматического play/pause другого устройства или общего пульта через presence.
- Отключение синхронизации отключает reporting и polling. Локальный пульт телефон-ТВ не меняется.
- Изменение клиентов защищено проверками API: старый сервер без endpoint не мешает приложению. До server deploy карточка не появляется.
- Этот PR включает только presence server, reporting и карточки. Production deploy выполняется отдельно через `deploy.sh` с backup. Бета не выпускается в этом PR: она запланирована после клиентского V2 и проверки полной связки.

## 9. Проверки

- Unit: валидация, TTL, session ordering, изоляция аккаунтов и clear.
- Billing integration: device auth, POST/GET, WS presence, read-only и revoked device.
- Client: snapshot mapping, session replacement, offline no-op, polling cleanup, self filtering и continue action.
- Полные root и billing tests, `npm run build`, `npm run build:mobile`, UI screenshot телефона.
- Независимое ревью и Greptile, все подтвержденные замечания исправляются.
