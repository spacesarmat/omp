# Visual Layout Editor Design

Дата: 2026-11-11
Статус: ожидает подтверждения Andy
Ветка: `feat/visual-layout-editor`

## 1. Назначение

Превратить существующий OMP Design Editor в полноценный визуальный редактор страниц и шаблонов. Пользователь должен редактировать каждый видимый элемент, менять порядок внутри контейнера, свободно размещать элементы по координатам и проверять результат на всех поддерживаемых платформах до экспорта.

Выбран гибридный layout: структурный порядок в потоке документа и свободное абсолютное позиционирование сохраняются независимо для платформы и ориентации.

## 2. Цели

- Сделать доступными для layout-редактирования все видимые элементы, включая контейнеры, текст, карточки, controls и legacy-шаблоны.
- Поддержать перетаскивание, изменение порядка, свободные X/Y, размеры и выравнивание.
- Сохранить реальные Preact-компоненты и текущую систему tokens, overrides, snapshots, drafts, rebase и защищённого экспорта.
- Сделать preview и экспорт детерминированными и одинаковыми.
- Не допустить скрытого изменения настроек приложения при работе в design mode.
- Сохранить совместимость со старыми темами и черновиками.

## 3. Не входит в задачу

- Совместное редактирование несколькими пользователями и серверный backend.
- Произвольный JavaScript, HTML или CSS от пользователя.
- Автоматический деплой, релиз и публикация экспортированных изменений.
- Замена реальных экранов статическими макетами.
- Абсолютное позиционирование всех элементов по умолчанию.
- Скрытое добавление зависимостей или активация layout runtime в production без явного export и проверки diff.

## 4. Анти-цели

- Позиции, которые без предупреждения ломают другую платформу или ориентацию.
- Потеря идентичности элемента после перерисовки, смены языка или reorder.
- Новый элемент управления, который срабатывает при выборе в редакторе.
- Молчаливая подмена layout-операции другим режимом.
- Экспорт, удаляющий или перезаписывающий чужие файлы.
- Десять независимых функций с разными моделями undo и сохранения.

## 5. Рассмотренные подходы

### Гибридный layout, выбран Andy

Поток документа сохраняет порядок элементов. Свободные координаты являются отдельным режимом placement. Настройки разделены по target и format.

Плюсы: поддерживает оба требования, сохраняет адаптивность, позволяет предупреждать о перекрытиях.
Минусы: требует двух режимов и явных правил перехода между ними.

### Только структурный layout

Порядок и размеры без свободных координат.

Не выбран: не выполняет требование свободного размещения.

### Полностью абсолютный canvas

Каждый элемент имеет X/Y и размеры.

Не выбран: слишком рискован для phone, desktop и TV, требует ручной настройки каждого экрана и увеличивает вероятность перекрытий.

## 6. Единая модель данных

### 6.1 Совместимость

`ThemeDocument` получает необязательные поля `layout` и `stylePresets`. Старое значение `schemaVersion: 1` сохраняется, потому что старые документы остаются валидными, а новые поля optional. Валидатор принимает только документированные поля и значения.

Старые snapshot и draft загружаются с пустыми layout-коллекциями. Rebase обрабатывает layout по стабильным `id`, как overrides, и сообщает о конфликтах по конкретному элементу.

### 6.2 Идентичность элементов

Существующий `data-design-id` продолжает обозначать тип для theme overrides. Новый `data-layout-node` уникально обозначает экземпляр внутри страницы.

Приоритет стабильного ключа:

1. Явный source key: `focusKey`, `data-row`, `data-action` или документированный component key.
2. Зарегистрированный ключ адаптера для контейнеров и текстовых блоков.
3. Детерминированный структурный путь с типом элемента и исходным sibling index.

Adapter сохраняет ключ на DOM-узле и в `WeakMap` между mutations. Начальный порядок вычисляется до применения layout, поэтому reorder не меняет идентичность. Смена языка не меняет ключ. Пользовательские дубликаты получают новый UUID и не зависят от текста.

Элементы без theme definition получают layout-only запись в LayersPanel. Отсутствие theme fields не запрещает перемещение, размеры, скрытие и выравнивание.

### 6.3 LayoutContainer

Каждый контейнер содержит:

- `id`.
- `target`, `screenId`, `format`.
- `nodeId` контейнера.
- `order`: упорядоченные `nodeId` детей в потоке.
- `direction`: `row`, `column` или `auto`, только если поддерживается реальным компонентом.
- `padding`, `alignment` и `distribution` через существующие layout tokens и ограниченный набор layout-свойств.

Экспорт порядка использует общий runtime layout adapter, а не CSS `order` для произвольных блоков. Adapter применяет порядок к реальному DOM в preview и там, где экспорт явно включает layout runtime.

### 6.4 LayoutPlacement

Каждое размещение содержит:

- `id`, `target`, `screenId`, `format`, `nodeId`.
- `mode`: `flow` или `absolute`.
- `x`, `y` в px от padding box контейнера для absolute.
- `anchor`: `top-left`, `top-right`, `bottom-left`, `bottom-right`.
- `width`, `height`: `auto` или ограниченное число px.
- `minWidth`, `maxWidth`, `minHeight`, `maxHeight` при наличии.
- `zIndex` в ограниченном диапазоне.
- `hidden`: влияет на preview и export.
- `locked`: запрещает случайное изменение только в редакторе и не меняет production CSS.
- `label`: пользовательское имя слоя.

Координаты и размеры не наследуются молча между платформами. Новый target/format начинает с flow или с явно скопированного placement.

## 7. Функциональные требования

### 7.1 Перемещение и порядок

- Drag внутри canvas показывает insertion line и будущий контейнер.
- LayersPanel поддерживает reorder и смену родителя, если тип контейнера это разрешает.
- Свободный режим включается явной командой или перетаскиванием в свободную область.
- `Arrow` двигает на 1 px, `Shift+Arrow` на 10 px.
- Переход flow -> absolute сохраняет текущий экранный прямоугольник как начальную позицию.
- Переход absolute -> flow спрашивает место в порядке через выбранную insertion point, без молчаливого сброса.
- Один завершённый drag равен одному undo-шагу.

### 7.2 Размеры и layout

- Handles изменяют ширину и высоту относительно выбранного anchor.
- Padding и margin редактируются визуально и численно.
- Ограничения компонента не дают задать невалидные или отрицательные размеры.
- Выравнивание и распределение в flow используют контейнерные свойства, в absolute используют координаты.
- Редактор не использует запрещённые проектом TV CSS: flex `gap`, `aspect-ratio`, `inset`, `:has`.

### 7.3 Multi-select

- `Shift+click` добавляет и убирает элементы.
- Рамка выбирает только полностью или частично входящие элементы по явному режиму.
- Общие свойства применяются одной транзакцией.
- Несовпадающие значения показываются как `mixed`.
- Выравнивание доступно по краям и центру, распределение при не менее трёх элементов.
- Групповое действие не затрагивает locked слои и сообщает об этом.

### 7.4 Направляющие и прилипание

- Линейки, включаемая сетка и шаг сетки.
- Guides для центров и краёв элементов и контейнеров.
- Snap к сетке, элементам и безопасной области; `Alt` временно отключает snap.
- Перекрытия и выход за безопасную область подсвечиваются, но absolute mode не запрещается автоматически.
- TV safe area учитывается отдельно от физического viewport.

### 7.5 Слои

- Дублирование, скрытие, блокировка и переименование.
- Поиск по имени, типу и nodeId, фильтры hidden/locked/component.
- Копирование и вставка внутри страницы и между страницами.
- Вставка между страницами создаёт новый nodeId и показывает несовместимые действия компонента до сохранения.
- Hidden не удаляет данные, undo восстанавливает все операции.

### 7.6 Копирование стилей

- Copy/Paste Style переносит только tokens и поддерживаемые layout-свойства, не nodeId и не action.
- Отдельный сброс каждого свойства.
- Перенос между платформами показывает список несовместимых свойств; ничего не отбрасывается молча.
- Вставка создаёт или обновляет документированный override и один undo-шаг.

### 7.7 Библиотека tokens

- Панель цветов, типографики, отступов и радиусов.
- Именованные `StylePreset` содержат только существующие разрешённые tokens.
- Поиск использования token по страницам и платформам.
- Применение preset создаёт документированный override.
- Изменение preset не меняет уже применённые overrides задним числом, если пользователь явно не выбрал обновление использования.

### 7.8 Сравнение платформ

- Два или три preview рядом с независимыми target, format и language.
- Синхронный выбор nodeId, state и показ guides.
- Один общий draft, отсутствие гонок autosave и независимые fixture cleanup.
- Режим portrait/landscape доступен без изменения активного preview вне compare.
- Тяжёлые TV и phone preview остаются lazy-loaded.

### 7.9 Доступность и геометрия

- Проверка контраста текста, controls и focus indication.
- Проверка минимального шрифта и target size по правилам проекта.
- Проверка переполнения, перекрытия интерактивных элементов и выхода за viewport/safe area.
- Предупреждения отображаются у элемента и в общем списке.
- Ошибки контраста и обязательных размеров блокируют export по существующим правилам; геометрические предупреждения требуют явного подтверждения.

### 7.10 Экспорт

- Перед записью доступен diff theme/layout/generated files.
- Можно экспортировать всё, выбранную страницу или выбранный component scope.
- Экспорт показывает затронутые платформы и конфликты.
- Manifest разрешает запись только владельческим файлам и не удаляет чужие изменения.
- Частичный экспорт не удаляет остальные overrides/layout и не перезаписывает unrelated generated files.
- Экспорт не запускает deploy или release.

## 8. Архитектура

### `design/schema.ts`, validation и defaults

Добавляют layout/preset типы, ограничения, миграцию и детерминированную сериализацию.

### `design/layout.ts`

Чистые операции: reorder, reparent, place, resize, align, distribute, duplicate, hide, lock, copy/paste и проверки границ. Не зависит от DOM и покрывается unit-тестами.

### `desktop/src/preview/designElements.ts`

Расширяется registry всех видимых элементов, стабильными ключами, layout attributes и runtime применением order/placement. Не выполняет реальные actions в design mode.

### `editor/src/layout`

Selection model, drag transaction, guides, snapping, geometry, clipboard и групповые операции. Pointer events переводятся в координаты native artboard с учётом zoom и pan.

### `editor/src/components`

Новые LayoutInspector, SelectionOverlay, Rulers, TokenLibrary, CompareWorkspace и расширенные LayersPanel/ExportPanel. Существующие ThemeInspector, SnapshotPanel и BaseReviewPanel используют общую модель.

### `editor/src/drafts.ts`

Поддержка составных транзакций: drag, group edit и paste создают ровно одну историю. Autosave, revision recovery, snapshots и rebase включают новые поля.

### `design/generate.ts`, `editor/export.mjs`

Детерминированный CSS для placement, layout manifest, scoped export и diff. В CSS не попадают editor-only lock, selection, guides и clipboard.

## 9. Правила взаимодействия

- Design click выбирает до child handler и не меняет реальные настройки.
- Текстовые поля сохраняют focus и typing.
- Drag начинается только после порога, чтобы не конфликтовать с click и text selection.
- Locked элемент можно выбрать в LayersPanel, но нельзя изменить до разблокировки.
- Hidden элемент выбирается через LayersPanel, не через canvas.
- Все операции используют актуальные selection после undo/redo и удаляют несуществующие nodeId из selection.
- Смена target/page сохраняет независимый layout и очищает только невалидный transient selection.

## 10. Безопасность и ограничения

- Нет произвольного CSS/JavaScript и сетевых вызовов из fixtures.
- Все числа, enum, id и размеры коллекций валидируются.
- Clipboard ограничен документированной схемой и лимитами.
- Экспорт сохраняет существующие loopback auth, same-origin, baseCommit, revision, manifest и process lock.
- Новые UI-тексты используют только дефис.
- TV UI остаётся одинаковым на 1080p и 4K, шрифт не менее 24px, кроме разрешённых тестовых подписей.

## 11. Проверки

- Unit: schema, layout operations, identity, alignment, snapping, clipboard, token usage, diff и export scopes.
- Component: selection, drag, multi-select, layers, inspector, compare, undo/redo, snapshots и recovery.
- Integration: реальные phone/TV/desktop controls не выполняют actions, inherited tokens сохраняются, export и preview совпадают.
- Regression: все предыдущие editor, design и desktop shell тесты остаются зелёными.
- Browser: phone portrait/landscape, desktop 1280x720, TV 1920x1080 и 4K, compare mode, drag/zoom/pan, keyboard-only operation.
- Стандартные проверки: `npm run test:editor`, точечные новые наборы, `npx tsc --noEmit`, `npm run build:editor`, `npm run editor:generate -- --check`, `git diff --check`.
- Полный `npm test` локально на Windows не запускать, полная проверка выполняется в CI на Linux.

## 12. Этапы поставки

1. Layout schema, стабильная идентичность, flow reorder и absolute placement.
2. Resize, multi-select, guides, snapping и layer operations.
3. Copy/Paste Style, token library и compare workspace.
4. Accessibility, geometry, scoped diff export, документация и браузерные проверки.

Каждый этап сохраняет работающий редактор и зелёные тесты. Все этапы входят в один PR только после полного выполнения и проверки.

## 13. Решения после независимой builder check

### Production runtime, выбрано Andy

Andy выбрал вариант 2: экспорт не ограничивается артефактами `design/`. Layout runtime подключается к production phone, TV и desktop.

- Общий runtime используется в preview и production, чтобы исключить расхождение порядка, placement, constraints и generated CSS.
- Production runtime активируется только после явного export с проверенным diff. Само открытие редактора и сохранение draft production не меняет.
- Изменения production экранов ограничены регистрацией layout nodes и вызовом общего runtime. Реальные actions, данные и бизнес-логика не переписываются.
- Экспорт обновляет документированные integration points в `src/`, `mobile/src` и `desktop/src`, но не создаёт произвольный runtime-код из пользовательского ввода.
- Layout runtime не включается автоматически при обновлении приложения, пока соответствующий layout не экспортирован.
- Обязательные проверки дополняются `npm run build`, `npm run build:mobile`, `npm run build:desktop`, production unit/integration tests и TV 1080p/4K.
- CI `build`, `android`, `billing` и desktop smoke обязателен перед PR merge. Устройства, деплой и релиз не затрагиваются без отдельных команд Andy.

### Динамические списки

Редактирование отдельных элементов динамических списков входит в задачу.

- Identity использует стабильные ключи данных, например infohash, server id или документированный item id.
- Повторный ключ данных является ошибкой fixture и проверки, а не поводом молча выбрать sibling index.
- Для статических компонентов без data key используется явный зарегистрированный ключ адаптера.
- Элемент, временно отсутствующий в данных, сохраняет layout. При повторном появлении с тем же ключом placement восстанавливается.
- Reorder одного элемента динамического списка в preview работает через layout runtime, не через изменение бизнес-данных. Production применяет тот же порядок после загрузки данных.
- Если тип элемента нельзя стабильно идентифицировать, редактор показывает ошибку регистрации до сохранения. Скрытая привязка к изменчивому DOM index запрещена.

### Поставка

Все четыре этапа входят в один PR `feat/visual-layout-editor`, поскольку это одно дополнение с общей схемой. Каждый этап завершается отдельным коммитом и зелёными проверками. PR создаётся только после реализации всех десяти функций.

Этот раздел заменяет неоднозначность разделов 6.3 и 7.10: общий runtime обязателен и в preview, и в production после явного export.
