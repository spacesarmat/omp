# Realtime-синхронизация устройств: проект

Дата: 2026-11-20
Статус: проект для согласования, продуктовый код не менять до одобрения

## 1. Цель

Сделать синхронизацию данных OMP между телефоном, LG, Android TV и desktop realtime, offline-first и устойчивой к потере данных.

Пользователь должен видеть на других устройствах:

- текущий просмотр и актуальную позицию;
- изменения истории, прогресса, пропусков, озвучки, названий и совпадений TMDB;
- состояние устройств и задержку синхронизации;
- понятное продолжение просмотра без автоматического перехвата воспроизведения.

Главное свойство системы: ни offline-работа, ни повтор запроса, ни гонка устройств, ни перезапуск приложения не должны молча терять изменение.

## 2. Не цели

- Не синхронизировать видео и звук кадр в кадр между устройствами.
- Не делать watch party и общий пульт воспроизведения.
- Не синхронизировать пароли TorrServer, токены устройств, ключи трекеров и billing-секреты.
- Не переносить всю медиатеку и файлы торрентов в realtime-канал.
- Не требовать постоянного интернета для локальных операций.

Presence означает «что и где сейчас играет», а не общий медиатайминг.

## 3. Текущая основа

Сейчас есть два независимых канала:

1. `POST /v1/sync` использует `SyncRecord`, LWW по `updatedAt`, разрешение ничьих по `deviceId`, tombstone и cursor `seq`.
2. `/v1/progress` хранит позицию по названию и серии для «Продолжить» и перезаписывается последним пришедшим запросом.

Локальные записи лежат целиком в Bag внутри `localStorage` и зеркалятся в IndexedDB. Изменения библиотеки, ожидающие список торрентов, временно находятся в `parked` в памяти.

Новый проект должен сохранить работающие экраны и постепенно заменить транспорт и хранение, а не переписывать приложение одним изменением.

## 4. Подходы

### 4.1. Только WebSocket

Плюсы: быстрый двусторонний канал.

Минусы: сложный запуск, нет простого восстановления через HTTP, больше изменений одновременно.

Не выбран как единственный транспорт.

### 4.2. Только HTTP long polling

Плюсы: проще прокси и отладка.

Минусы: больше задержка и накладные расходы, сложнее presence и heartbeat.

Не выбран.

### 4.3. Серверные ревизии, WebSocket и HTTP fallback

Выбран этот подход:

- сервер назначает revision каждой мутации;
- WebSocket доставляет изменения и presence;
- HTTP `/v2` выполняет те же операции при недоступном WebSocket;
- IndexedDB хранит записи, outbox и cursor;
- старый `/v1/sync` продолжает работать на переходном этапе;
- функция включается постепенно и может быть выключена без потери данных.

## 5. Основные решения

### 5.1. Revision вместо cursor, зависящего от commit race

Для каждого аккаунта ведется монотонная последовательность revision. Ее источником является строка `device_sync_counters(account_id, next_revision)`.

На каждую принятую мутацию в одной транзакции:

- сервер проверяет `mutationId`;
- выполняет `INSERT ... ON CONFLICT DO UPDATE` для account counter и получает revision через `RETURNING`;
- блокировка строки counter удерживается до commit, поэтому записи одного аккаунта проходят через commit по очереди;
- обновляет текущий snapshot;
- добавляет запись в change log;
- сохраняет результат `mutationId`;
- возвращает ack с revision после commit;
- рассылает изменение подключенным устройствам аккаунта.

Нельзя заменять row lock простым `nextval` или чтением `MAX(revision)`: sequence может быть зарезервирована другой транзакцией, которая еще не видна клиенту. Клиентские часы не участвуют в порядке доставки и cursor.

### 5.2. Идемпотентные мутации

`mutationId` формируется как устойчивый UUID или пара `deviceId` и монотонный локальный counter.

Повтор одного `mutationId` возвращает исходный результат и не создает новое изменение.

Это обязательно для повторов после таймаута, перезапуска и потери ответа.

### 5.3. Конфликты по смыслу данных

Общий revision определяет порядок синхронизации, но не заменяет правила слияния.

Предлагаемые правила:

- `progress`: playback session, monotonic sequence внутри сессии, явная операция перемотки;
- `skip`, `audio`, `title`, `watch`, `quality`, `match`: LWW по полям с Hybrid Logical Clock и `deviceId` как tie-breaker;
- `journal`: одна запись на файл и источник, удаление остается tombstone;
- presence: ephemeral, не участвует в LWW и не пишется на каждый heartbeat в Postgres.

HLC хранит physical time, logical counter и device id. `serverTime` помогает обнаруживать скачок часов, но не используется как единственная защита.

Режим совместимости со старыми клиентами имеет приоритет. Пока аккаунт могут изменять `/v1` клиенты, каноничным остается текущий whole-record LWW по `updatedAt` и `deviceId`. Общий mutation service применяет один результат к `/v1` snapshot и `/v2` change log. Новые записи `/v2` проецируются обратно в `/v1`, а записи `/v1` получают server revision и mutation id при импорте. Per-field merge нельзя смешивать с whole-record записью старого клиента: он включается только для типа данных после прекращения его записи через `/v1`.

### 5.4. Playback session

Каждый запуск воспроизведения получает `sessionId`.

Позиция содержит:

- `sessionId`;
- `titleKey`, `episodeKey`, hash и file id, когда они известны;
- `positionSec`, `durationSec`;
- `state`: playing, paused, finished;
- монотонный `positionSeq`;
- время операции и устройство.

Поздний пакет старой сессии не может перезаписать новую сессию. Внутри одной сессии поздний пакет с меньшим `positionSeq` отбрасывается.

При одновременном просмотре на двух устройствах пользователю показывается выбор, автоматически воспроизведение не перехватывается.

## 6. Протокол `/v2`

### 6.1. HTTP fallback

Предлагаемые операции:

- `POST /v2/sync/mutations` - batch мутаций и ack;
- `GET /v2/sync/changes?after=<revision>&limit=500` - догрузка;
- `GET /v2/sync/snapshot` - начальное состояние или восстановление;
- `POST /v2/sync/presence` - fallback для устройств без WebSocket.

Ответы содержат `revision`, `serverTime` и признак наличия следующей страницы.

### 6.2. WebSocket

Endpoint: `/v2/sync/ws`.

Токен не помещается в URL и не пишется в лог. После подключения клиент отправляет auth-сообщение с device token. До успешной авторизации сервер не отправляет данные и закрывает неактивное соединение по короткому таймауту.

Основные сообщения:

- `auth` и `ready`;
- `resume` с последним revision;
- `mutations` и `ack`;
- `changes`;
- `presence`;
- `ping`, `pong`;
- `error` с кодом, без секретов и содержимого записей.

Предлагаемые параметры:

- auth timeout 5 секунд;
- heartbeat 25 секунд;
- reconnect с экспоненциальной задержкой и jitter;
- до 200 мутаций в batch;
- существующий предел body 8 КБ сохранить на первом этапе;
- ограничения сообщений, соединений и backpressure по аккаунту и устройству.

### 6.3. HTTP остается обязательным

WebSocket недоступен или потерян:

- локальные операции продолжают записываться в outbox;
- клиент использует HTTP `/v2`;
- при восстановлении канала выполняется resume по revision;
- пользовательские данные не блокируются состоянием сокета.

## 7. Схема Postgres

Новые таблицы предлагаются дополнительно к существующим.

### `device_sync_changes`

- `account_id`;
- `revision`;
- `record_id`;
- `kind`;
- `mutation_id`;
- `body` или ссылка на snapshot;
- `deleted`;
- `author_device_id`;
- `created_at`.

Первичный ключ `(account_id, revision)`. Индекс `mutation_id` нужен для связи с результатом, но срок жизни change log не определяет идемпотентность.

### `device_sync_counters`

Одна строка на аккаунт с `next_revision`. Обновление строки назначает revision и сериализует записи аккаунта до commit.

### `device_sync_mutations`

Отдельное хранилище уже принятых результатов:

- `account_id` и `mutation_id` как уникальный ключ;
- сериализованный ack или исходный результат;
- `revision`;
- `created_at`;
- `expires_at`.

Эта таблица не очищается вместе с change log. Повтор существующего `mutationId` всегда возвращает сохраненный результат. После `expires_at` V2-повтор отклоняется как `mutation_expired` без применения данных. Клиент обязан получить текущий snapshot, переоткрыть конфликт как новую мутацию и не применять старый outbox автоматически. Для старого `/v1` просроченный deterministic retry возвращает сохраненный ack без применения старого body и не блокирует остальные записи batch: у такого клиента нет V2 recovery flow.

### `device_sync_state`

Текущий snapshot записи:

- аккаунт и record id;
- тип и ключ;
- тело;
- tombstone;
- последний revision;
- HLC и устройство автора.

Существующая `device_sync` сохраняется на переходном этапе для старых клиентов.

### `device_sync_cursors`

Последний ack каждого устройства для compaction и диагностики отставания.

### Presence

На первом этапе только память процесса с TTL. Постоянными остаются paused, finished и явный exit. Играющие heartbeat не записываются в Postgres.

Если появится несколько billing-процессов, добавить Postgres LISTEN/NOTIFY или отдельный broker. Для текущего одного процесса broker не требуется.

## 8. Локальное хранилище

IndexedDB становится источником истины для синхронизации.

Object stores:

- `records` - одна запись на id;
- `outbox` - мутации, ожидающие ack;
- `meta` - account, revision, HLC, device counter;
- `presence` - необязательный временный cache.

Требования:

- одна транзакция объединяет изменение записи и outbox;
- никакого перезаписывания всего Bag на каждую операцию;
- один sync leader на устройство через `BroadcastChannel` и lease, когда API доступен;
- на старом webOS без `BroadcastChannel` используется IndexedDB lease и `storage` events, а при надежной работе только одной вкладки достаточно lease;
- остальные вкладки получают изменения через доступный broadcast-механизм;
- `localStorage` временно остается проекцией для старых экранов.

Поддерживаемый минимум платформы не повышается. Перед включением `/v2` клиент проверяет IndexedDB, транзакционную запись, WebSocket и нужные fallback. Если устройство не проходит capability check, оно остается на текущем `/v1` и localStorage projection. Это не блокирует `/v2` на остальных устройствах аккаунта.

Загрузка библиотеки всегда повторно строит проекцию из сохраненных records. In-memory `parked` больше не является единственным мостом между sync и экраном.

## 9. Presence и UX

Первый минимальный UX:

- «Сейчас играет на LG» с названием, серией и позицией;
- кнопка «Продолжить здесь»;
- состояние «Синхронизировано», «Offline, N изменений в очереди», «Отстает на N секунд»;
- предупреждение при активной другой сессии вместо автоматического переключения.

Никаких уведомлений на каждый heartbeat.

## 10. Совместимость и миграция

### Этап 0. Подготовка без изменения поведения

- fault-injection тесты текущего sync;
- метрики pending, cursor, задержки и конфликтов;
- тест на повторное применение records после перезапуска;
- фиксация baseline нагрузки и размера таблиц.

### Этап 1. Локальный фундамент

- IndexedDB records, outbox и meta;
- sync leader для вкладок;
- восстановление проекции библиотеки;
- экраны продолжают работать через текущие projections.

### Этап 2. Серверный `/v2`

- revision, change log, idempotency;
- HTTP `/v2`;
- общий mutation service для `/v1` и `/v2`;
- двойная запись старого и нового формата;
- миграция существующих строк.

Отдельный `/v1/progress` и таблица `playback_progress` сохраняются на весь переходный период. Новые клиенты проецируют свои позиции в этот endpoint, чтобы старые устройства продолжали показывать «Продолжить».

Старый протокол не содержит `sessionId` и `positionSeq`, поэтому гарантировать порядок двух legacy-запросов невозможно. Правило совместимости:

- во время активной `/v2` сессии для того же аккаунта, названия и серии legacy-запись меняет только `playback_progress` для старых клиентов и не заменяет активную `/v2` сессию;
- когда активной `/v2` сессии нет, legacy-запись может обновить legacy continuation в `/v2` в порядке прихода на сервер;
- после paused или finished новая запись старого устройства снова считается допустимым продолжением;
- защита от позднего ответа внутри `/v2` не распространяется на старый `/v1` клиент без sequence. Для таких клиентов сохраняется прежнее поведение last arrival wins.

Для старого клиента его endpoint и ограничение в 200 строк не меняются. Локальный канал resume телефон-ТВ без billing остается нетронутым.

### Этап 3. Realtime

Серверная часть `/v2/sync/ws` использует тот же Node HTTP-процесс и mutation service, что и `/v1` и `/v2`. События рассылаются только после PostgreSQL commit, resume догружает все исторические страницы перед live-буфером. Доступ устройства перепроверяется для команд, heartbeat и live-доставки. Auth timeout 5 секунд, heartbeat 25 секунд, payload 8 КБ, входящая очередь 20 сообщений, лимиты 20 соединений на аккаунт и 5 на устройство. Read-only режим отклоняет Upgrade. Существующий Caddy `reverse_proxy` передает Upgrade без изменения конфигурации. Клиентский V2 еще не включен.

Playback presence работает через `/v2/sync/presence` и WS-сообщения. Каталог живет в памяти процесса с TTL 90 секунд, heartbeat не пишется в Postgres. ТВ сообщает фактический snapshot, телефон keepalive встроенного 2160 Player. Настройки аккаунта показывают карточки других устройств и явное «Продолжить здесь» без автоматического перехвата.

- WebSocket и resume;
- presence;
- новый клиент под feature flag;
- HTTP fallback и восстановление после обрыва.

### Этап 4. Расширенное слияние

- playback sessions;
- HLC и per-field merge только для типов, которые больше не записываются через `/v1`;
- понятный UX конфликтов.

### Этап 5. Завершение

- beta с ограниченной группой;
- включение по умолчанию после проверки метрик;
- прекращение двойной записи только после исчезновения поддерживаемых старых клиентов;
- удаление `/v1` отдельным решением, не автоматически.

## 11. Откат

- Feature flag отключает WebSocket и новый клиентский путь.
- HTTP `/v1` и `/v2` продолжают работать в переходный период.
- Двойная запись позволяет вернуть старое приложение без потери новых изменений.
- Новые таблицы при откате не удаляются.
- Миграция на NUC выполняется только после backup и отдельного согласования deploy.

## 12. Очистка и квоты

- Change log удаляется только после ack всех активных устройств и минимального срока хранения.
- Предлагаемый минимум change log: 30 дней.
- Предлагаемый срок tombstone после полного ack: 90 дней.
- `device_sync_mutations` хранится не менее 180 дней и не зависит от очистки change log. После срока `mutationId` отклоняется без применения, клиент делает rebase через snapshot.
- Неактивное устройство не должно вечно блокировать compaction: после отдельного срока ему потребуется snapshot.
- Ограничения по записям, batch, body и общему объему на аккаунт.

Точные значения подтвердить на реальных размерах перед реализацией.

## 13. Наблюдаемость

Метрики без содержимого пользовательских записей:

- число соединений и reconnect;
- revision lag по устройству;
- outbox size и возраст старейшей мутации;
- ack latency;
- число повторов `mutationId`;
- конфликты и clock skew;
- активные playback sessions;
- задержка broadcast;
- длительность транзакции и ошибки БД;
- размер change log и результат compaction.

Админка показывает агрегаты, не тела записей и не токены.

## 14. Тестовая стратегия

Обязательные автоматические сценарии:

- два устройства меняют одну запись одновременно;
- два commit получают revision в противоположном порядке завершения;
- ответ на mutation потерян и клиент повторяет запрос;
- процесс падает до и после commit, ack и cursor update;
- часы одного устройства ушли вперед и назад;
- offline-изменения сливаются после reconnect;
- WebSocket отключается во время batch;
- старый `/v1` клиент и новый `/v2` клиент работают одновременно;
- запись приходит до списка библиотеки, затем приложение перезапускается;
- две вкладки одного устройства работают одновременно;
- поздний пакет старой playback session не меняет позицию;
- compaction не удаляет нужное отстающему устройству изменение.

Ручной стенд:

- S21 и LG;
- Android TV;
- desktop и вторая вкладка;
- выключение сети, блокировка телефона, перезапуск ТВ-приложения;
- обновление со старого клиента и откат feature flag.

## 16. Решения, принятые как рабочие значения по умолчанию

Это предложения проекта, а не уже подтвержденные пользователем решения:

- WebSocket плюс HTTP fallback, а не SSE;
- server revision для доставки и HLC только после выхода соответствующего типа из `/v1` режима;
- во время смешанной флотилии каноничный whole-record LWW сохраняется;
- in-memory presence для одного billing-процесса;
- IndexedDB как источник истины и sync leader на устройство при поддержке capability check;
- старые webOS без нужных возможностей остаются на `/v1`, минимальная платформа не повышается;
- двойная запись `/v1` и `/v2` на переходном этапе;
- `/v1/progress` и локальный resume телефон-ТВ сохраняются на переходный период;
- никакого автоматического перехвата воспроизведения;
- realtime данных и presence, но не синхронный показ видео.

## 17. Критерий готовности проекта к реализации

Перед первым продуктовым PR нужно:

- согласовать этот документ;
- подтвердить состав синхронизируемых типов и политику конфликтов;
- зафиксировать протокол сообщений и схему миграции;
- подготовить отдельный implementation plan с файлами, тестами и точками отката;
- не менять NUC и production без отдельного разрешения.
