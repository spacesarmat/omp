# Подписки OMP и Jackett

Панель (React + shadcn/ui + Tailwind), бот Telegram и API, через которое телефон ищет в Jackett. Ключ Jackett на телефон не уходит. Состояние - Postgres 17 (`BILLING_DATABASE_URL`).

## Локально на ПК

```
cd ops/billing
npm run build:admin   # один раз после правок admin/
node src/server.mjs
```

Панель: `http://127.0.0.1:8787/admin`. Вход только через Telegram (id администраторов - в настройках). Ссылка входа живёт 10 минут. Аварийная одноразовая ссылка с этой машины: `npm run admin-login-link` (10 минут, один раз, в журнале актор `cli`). Пароль панели больше не используется.

`BILLING_BOT_POLL` по умолчанию `1`: процесс вызывает `getUpdates`. На VPS это должно быть включено ровно у одного контейнера. NAS-compose ставит `0`. Локальный `node src/server.mjs` рядом с боевым ботом тоже запускайте с `BILLING_BOT_POLL=0`, иначе второй экземпляр заберёт `/start admin_…` и ответит «ссылка устарела» на чужой токен. Если этот процесс - единственный billing, оставьте `1`. Конфликт 409 (`terminated by other getUpdates request`) пишется в лог не чаще раза в минуту и, если включены уведомления администраторов, один раз в час уходит в Telegram. Вкладка **Сервисы** показывает время последнего успешного getUpdates и был ли такой 409 за последние 15 минут. Значения `0`, `false`, `off`, `no` выключают опрос; любое другое, включая пустое, оставляет его включённым. Перезапустите процесс после смены переменной.

Опрос всегда передаёт `allowed_updates=["message","callback_query","channel_post"]`: Telegram запоминает последний список типов (в том числе из `setWebhook`), и без явного списка бот мог бы перестать получать нажатия кнопок. На токене этого бота нельзя ставить webhook и нельзя вызывать `getUpdates` из других программ. Этим же ботом workflow релиза публикует пост в канал и закрепляет его; служебную строку «… закрепил сообщение» в канале удаляет billing (канал `@ompplyaer`, переменная `BILLING_CHANNEL` - другой `@канал` или числовой id, пустое значение - не трогать канал). Бот должен быть админом канала с правом удалять сообщения.

## Docker на NAS (ZimaOS) - тест в домашней сети

1. Скопируй каталог `ops/billing` на NAS (SMB / Git).
2. В ZimaOS → Docker → Compose (или SSH на NAS): из этого каталога  
   `docker compose up -d`
3. Вход в панель - через Telegram. Если бот ещё не настроен, с NAS: `docker exec billing npm run admin-login-link` (или `node src/adminLoginLink.mjs` в каталоге сервиса). Команда печатает одноразовую ссылку на 10 минут и не пишет секрет в лог.
4. С телефона или ПК в той же Wi‑Fi открой `http://IP-NAS:8787/admin`.
5. В панели:
   - адрес Jackett: `http://jackett:9117` (имя сервиса в Docker);
   - API-ключ - из веб-интерфейса Jackett (его можно открыть временно, пробросив порт, или через `docker exec`);
   - цены можно поставить тестовые; бота и ЮMoney для домашнего теста не обязательны.
6. Выпусти код подписки в панели.
7. В приложении в `src/billing/config.ts` поставь `BILLING_ORIGIN = 'http://IP-NAS:8787'`, собери тестовый APK, введи код в «Источники поиска».

Jackett с хоста не торчит наружу - к нему ходит только контейнер billing.

## Публичный HTTPS - Caddy на VPS

Домен: **omp-player.online**. Панель и API: **`https://billing.omp-player.online`**.

Cloudflare Tunnel снят. Снаружи Cloudflare (оранжевое облако, SSL/TLS **Full (strict)**) ходит на Caddy на VPS. Caddy держит сертификат origin и проксирует контейнер `billing` на порту 8787. Лендинг, Jackett и JacRed - на том же Caddy. Стек и команды выкладки: `ops/vps/README.md`.

Проверка: `https://billing.omp-player.online/health` → `{"ok":true}`.

HSTS (`max-age=15552000; includeSubDomains`, без preload), `X-Content-Type-Options`, `X-Frame-Options` и `Referrer-Policy` ставит Caddy. Заголовка `Server` у origin нет.

### Локально и из мира

- Админка в LAN всегда: `http://192.168.1.191:8787/admin`
- Приложение ходит только на `https://billing.omp-player.online` (запасной LAN-адрес убран; `/go/`-ссылки бота - тоже на домен)
- ЮMoney: `https://billing.omp-player.online/v1/yoomoney`

## Настройки панели

Кошелёк ЮMoney, цены - вкладка **Настройки**. JacRed / Jackett / TorrServer (ops) - вкладка **Сервисы**: URL, вкл/выкл для подписчиков, health-probe. Телефон ходит только в `POST /v1/search` и `POST /v1/torrent` (ключи на устройстве не хранятся).

Вкладка **Изменения** - полный CHANGELOG из `main` на GitHub, включая пункты `[tech]`, которых нет в приложении, релизе и Telegram (правила маркеров - `docs/changelog-markers.md`). `GET /admin/api/changelog` только для вошедшего админа (иначе 401), работает и при `BILLING_READONLY`. Сервер берёт `CHANGELOG.md` и `CHANGELOG.en.md` с raw.githubusercontent.com, держит копию 10 минут, а если GitHub не ответил, показывает последнюю копию с пометкой и пробует снова не раньше чем через минуту. В образ billing CHANGELOG не входит.

### Секреты - только в `.env`

Секреты не хранятся в базе и не попадают в дампы. Панель показывает их только для чтения: «задан ✅, ****abcd» (последние 4 символа - только у значений от 12 символов) или «не задан», с подсказкой, где менять. Форма настроек их не принимает.

| Настройка | Переменная в `.env` |
| --- | --- |
| Токен бота | `BILLING_BOT_TOKEN` |
| Секрет ЮMoney | `BILLING_YOOMONEY_SECRET` |
| SMTP-пароль | `BILLING_SMTP_PASS` |
| Ключ API Jackett | `BILLING_JACKETT_API_KEY` |
| Ключ API JacRed | `BILLING_JACRED_API_KEY` |
| Пароль basic-авторизации индексаторов | `BILLING_INDEXER_PASS` |
| Ключ подписи токенов устройств | `BILLING_TOKEN_SECRET` (32+ символов) |

Поменять: строка в `.env` (права 600, владелец root), затем `docker compose ... up -d --no-deps billing`. При старте billing удаляет из базы копию каждого секрета, который задан в `.env` (и `kv.token_secret`, если задан `BILLING_TOKEN_SECRET`), и пишет в лог только имена. Пока секрета нет в `.env`, используется старое значение из базы, поэтому до переноса ничего не ломается.

Перенос с сервера, где секреты ещё в базе (значения не печатаются, только имена):

```sh
cd /opt/omp-vps && DC="docker compose -f docker-compose.yml -f docker-compose.nuc.yml"
sudo install -m 600 .env /opt/omp-backups/env-$(date +%Y%m%d-%H%M%S)      # копия .env
sudo sh -c "umask 077; $DC run --rm --no-deps -T billing node tools/secretsToEnv.mjs > /root/secrets.add"
sudo sh -c "cat /root/secrets.add >> .env && rm -f /root/secrets.add"
sudo $DC run --rm --no-deps -T billing node tools/secretsToEnv.mjs --verify  # каждая строка: same / env only
sudo $DC up -d --no-deps billing                                             # старт удаляет копии из базы
```

Старые дампы в `/opt/omp-backups` секреты ещё содержат: храните их как раньше, с правами 600.

## Устройства, активация, оплата

- В базовой подписке **2 устройства** (`DEVICE_BASE` в `src/logic.mjs`). Снимок без `meta.deviceBase` (записанный старым сервером) при первом чтении получает +1 к `deviceLimit` у каждой подписки: 1 → 2, купленный доп. слот сохраняется (2 → 3, а затем по миграции ниже - 2 + 1 помесячный слот). Метка `meta.deviceBase = 2` не даёт миграции сработать второй раз.
- Лимит соблюдается на сервере. Новый код создаётся, только пока привязанных устройств меньше лимита (см. «Лимит устройств» ниже), а свободный (ещё не введённый) код выдаётся повторно вместо нового. Промокод и «Выдать дни» при занятых слотах продлевают подписку без нового кода. «Выдать код» в админке отвечает ошибкой «Лимит устройств». `POST /v1/activate` для нового устройства сверх лимита отвечает `409 {"error":"device_limit"}`. Уже привязанные устройства работают как раньше, повторный ввод своего кода проходит.
- `POST /v1/activate` ограничен в памяти процесса: `BILLING_ACTIVATE_IP_MAX` (20) запросов с одного IP и `BILLING_ACTIVATE_CODE_MAX` (10) на один код за `BILLING_ACTIVATE_WINDOW_SEC` (600 с). `0` выключает ограничение. Сверх лимита - `429 {"error":"rate"}` и `Retry-After`. IP берётся из `CF-Connecting-IP`, затем из первого адреса `X-Forwarded-For`, затем из сокета.
- `POST /v1/link/clear`: если передан `Authorization: Bearer`, токен должен принадлежать этому `X-Device-Id`, иначе 401. `BILLING_LINK_CLEAR_REQUIRE_TOKEN=1` требует токен всегда. По умолчанию выключено: приложения до PR-5 шлют сюда только `X-Device-Id`, а у телефона, привязанного к Telegram без кода, токена нет. Включение - отдельным шагом, см. «Позже: `BILLING_LINK_CLEAR_REQUIRE_TOKEN=1`».
- `GET /v1/me` без действительного токена отвечает как раньше, но без списка устройств (`devices: []`).
- Уведомление ЮMoney с `unaccepted=true` записывается как платёж `pending` с ошибкой `unaccepted` и подписку не продлевает; администраторам уходит «Платёж ждёт подтверждения». Если потом придёт уведомление с тем же `operation_id` без `unaccepted`, оно применяется и заменяет запись.

## Админка: устройства, лимит, дни, платежи ЮMoney

Карточка пользователя (`/admin/?id=…`), код в `src/deviceAdmin.mjs`, экран в `admin/src/panels/DeviceAdmin.tsx`.

- **Устройства**: список берётся из реестра устройств (таблица `devices`, см. «Реестр устройств и токены») - время привязки, последнего обращения и последний IP, плюс «старый токен» / «новые токены». Отметка ставится на `POST /v1/search`, `POST /v1/torrent`, `GET /v1/me`, `POST /v1/token/*` с действительным токеном и при активации, не чаще раза в 10 минут на устройство (`SEEN_EVERY_MS`), одной строкой в `devices`, без перезаписи JSON-стейта. IP хранится уже усечённым, без последней части (`95.24.113.*`, IPv6 - первые три группы); полный адрес, записанный более ранней сборкой, обрезается при чтении базы (`migrateTruncatedIps`).
- **Отозвать** (с подтверждением, по id строки реестра): строка реестра и её refresh-токены отзываются, код отвязывается, сессия удаляется - и старый токен, и access-токен перестают работать сразу. Для освободившегося слота выпускается новый код. Пользователю с Telegram уходит короткое сообщение «Устройство … отключено администратором…».
- **Лимит устройств** - сумма трёх частей (`limitBreakdown` в `logic.mjs`), в боте, кабинете и админке видна разбивка «2 базовых + 1 бонусный (навсегда) + 1 купленный»:
  - **База** - `settings.baseDevices` (по умолчанию 2, 1-20; «Настройки» → «Цены»). Действует сразу для всех подписок без индивидуального лимита, тексты бота («до N телефонов») берут её же. Неверное значение не сохраняется, админка пишет ошибку. **Снижение базы** - только с подтверждением: админка сначала показывает, сколько платящих подписок без индивидуального лимита затронет и сколько устройств перестанет работать (`GET /admin/api/base-impact?base=N`), сервер без `confirm=yes` ничего не сохраняет и отвечает теми же цифрами; в журнал - «Базовых устройств: 2 → 1 (подписок затронуто: N, устройств отключено: M)».
  - **Индивидуальный лимит** - `limitOverride` подписки (1-20 или `null`). Если задан, заменяет базу и не меняется вместе с общей базой. Лимит = индивидуальный + действующие бонусные + купленные. В карточке пользователя поле «Индивидуальный лимит» (пусто = общая база), в списке подписок пометка «индивид.».
  - **Бонусные** - `bonusSlots`: строки `{id, count, until | null, reason, grantedAt, source: 'promo' | 'admin'}`. Бесплатно, в цену продления не входят, переживают смену базы. Строка с датой перестаёт считаться в момент `until` сама (без льготного периода), в админке остаётся с пометкой «истёк». Выдаются в карточке («Выдать бонус»: устройств, дней - пусто = навсегда, причина) и промокодом; снимаются кнопкой «Снять» с подтверждением. `POST /admin/bonus`, `POST /admin/bonus-remove` (`confirm=yes`).
  - **Купленные** - помесячные «доп.» (`extraSlots`, 0-20; выданные здесь действуют до `paidUntil` и продлеваются с подпиской), как раньше.
  - Понижение ничего не отвязывает: последние привязанные сверх лимита перестают работать. Если привязано больше лимита - предупреждение в карточке и на главной. Телефон в истёкшем бонусном слоте получает `device_limit`; `extra_expired` - только когда его держал бы не продлённый купленный слот.
  - `deviceLimit` в подписке больше не читается: он остаётся зеркалом базы на случай отката на образ до этой версии.
  - **Миграция** (`meta.limitModel`, один раз при первом чтении): подписка, чей `deviceLimit` отличается от базы, получает такой `limitOverride`, остальные - `null`; у всех появляется пустой `bonusSlots`. Ни у кого лимит не меняется. Подписка, у которой уже есть `limitOverride`, не трогается, повторный запуск ничего не меняет.
- **Промокод с бонусными устройствами**: «Бонусных устройств» и «Бонус на дней» (пусто/0 - навсегда, иначе N дней с момента активации). Промокод может давать только устройства (0 дней) - такой нужен действующей подписке, без неё бот пишет «Сначала оформите подписку», использование не тратится. В боте админа: `/admin_promo КОД ДНЕЙ АКТИВАЦИЙ [УСТРОЙСТВ [ДНЕЙ_БОНУСА]]`.
- **Имя устройства**: телефон шлёт модель (`Build.MANUFACTURER` + `MODEL`, «Xiaomi 2201117TY») полем `name` в `/v1/activate`, `/v1/token/refresh` и `/v1/token/upgrade`. Сервер оставляет буквы, цифры, пробелы и `. , - ( ) + /`, не больше 40 символов, и пишет в `devices.name`; пустое имя (старое приложение) прежнее не стирает. Бот («Устройства») и админка показывают его рядом с началом device id.
- **Убавить дни** (с подтверждением): `paidUntil` минус N дней, доп. слоты обрезаются до новой даты. Можно уйти в прошлое - тогда доступ закончится после льготного периода.
- **Ждут подтверждения в ЮMoney**: платежи с `unaccepted` (в карточке и во вкладке «Финансы», плюс предупреждение на главной). «Подтвердить платёж» применяет его ровно один раз, как пришедшее `accepted`-уведомление: повторный клик отвечает «Платёж уже обработан», а настоящее уведомление ЮMoney после этого - дубль. «Отклонить» убирает платёж из ожидания, ничего не продлевая; если ЮMoney потом всё же пришлёт `accepted`, он применится (один раз).
- **Смены устройства в боте**: «Отвязать» - не больше 2 раз за скользящие 30 дней (`SWAP_LIMIT`, `SWAP_WINDOW_MS`), каждое отвязанное устройство - одна смена. Дальше бот отвечает датой, с которой смена снова возможна. «Код» для свободного слота смену не тратит. Админ сбрасывает счётчик кнопкой «Сбросить счётчик» (`swapsResetAt`); отзыв устройства админом смену не тратит.
- Все действия пишутся в журнал (`audit`, с `accountId`) и показываются в «Ленте событий» на главной со ссылкой на карточку (кроме служебных «Показан код» и «Сохранены настройки» - они только в журнале); смены устройства в боте - там же, тип «устройство». Маршруты - `POST /admin/device-revoke|limit|subtract|swaps-reset|payment-confirm|payment-reject`, как и остальные `POST /admin/*`, требуют сессию админа и `csrf`; разрушающие - ещё `confirm: "yes"`.

## Реестр устройств и токены

Код в `src/registry.mjs`, тесты в `test/tokens.test.ts`. Телефон - `src/billing/tokens.ts` (см. «Телефон» ниже).

- **Реестр.** Таблицы `devices` (строка на каждую привязку кода к устройству: подписка, аккаунт, код, `device_id`, `bound_at`, `last_seen_at`, `last_ip_net`, `status`, причина отзыва) и `refresh_tokens` (только sha256, `expires_at`, `rotated_at`, `replaced_by`, `revoked`) в той же базе Postgres, рядом с состоянием. Состояние остаётся главным для кодов, лимитов и дней: `syncRegistry` в той же транзакции, что и каждая запись снимка, приводит реестр к привязкам (новая привязка - новая строка; отвязка, отзыв кода, перепривязка - строка `revoked` вместе с её refresh-токенами). Отозванная в реестре привязка обратно не создаётся. **Миграция**: первый запуск строит строки для всех привязанных кодов (с `lastSeen`/IP из кода); повторные - ничего не меняют.
- **Access-токен**: `a1.<payload>.<sig>`, payload - base64url JSON `{sub, dev, did, iat, exp}` (`dev` - строка реестра, `did` - хэш deviceId), подпись HMAC-SHA256. Живёт 24 ч (`ACCESS_TTL_MS`). Заголовка и `alg` нет, поэтому подмена алгоритма невозможна. При каждом запросе проверяются подпись, `exp`, deviceId и статус строки реестра - отзыв действует сразу. Ключ: `BILLING_TOKEN_SECRET` из `.env` (32+ символов, приоритетнее), иначе случайный ключ, созданный один раз в таблице `kv` базы. Смена ключа: текущие access-токены получают 401 `bad_token`, телефон берёт новый по refresh, ничего не отвязывается. Ключ короче 32 символов игнорируется (строка в stderr, без значения).
- **Refresh-токен**: `r1.` + 32 случайных байта, живёт 180 дней (`REFRESH_TTL_MS`), каждое использование выдаёт новый. Повтор уже использованного в течение 60 с (`ROTATE_GRACE_MS`), пока новый ещё не использован, - потерянный ответ: новый отзывается, выдаётся ещё одна пара. Любой другой повтор - **подозрение на клон, только отметка**: у строки растут `clone_at` / `clone_count`, в журнал и ленту - «Подозрение на клон: ключ устройства … использован повторно» (не чаще раза в час на устройство), в списке устройств админки - «возможен клон». Пара всё равно выдаётся, ничего не отзывается, пользователю ничего не уходит; отозвать устройство админ может сам.
- **Старые токены**: `BILLING_LEGACY_TOKENS` (по умолчанию `1`) - принимаются. `0` - старый токен получает 401 `legacy_disabled` на `/v1/search`, `/v1/torrent`, `/v1/me`, `/v1/link/clear`, активация без `"tokens": "pair"` - 403 `app_update_required`; `/v1/token/upgrade` работает, чтобы поздний телефон мог перейти.
- **Маршруты** (ответы с ошибкой - `401 {"error": …}`; `bad_token`, `token_expired`, `refresh_expired`, `revoked`, `upgraded`, `legacy_disabled`; не больше `BILLING_TOKEN_IP_MAX` = 60 запросов за 10 минут с одного IP, дальше 429):
  - `POST /v1/activate` с `"tokens": "pair"` - вместо непрозрачного `token` отдаёт `{refreshToken, accessToken, accessExpiresAt, refreshExpiresAt, paidUntil}`. Без этого поля ответ прежний.
  - `POST /v1/token/refresh` `{refreshToken}` + `X-Device-Id` - новая пара.
  - `POST /v1/token/upgrade` с `Authorization: Bearer <старый токен>` + `X-Device-Id` - один раз меняет старый токен на пару. Старый после этого работает ещё 60 с, повтор в эти 60 с выдаёт новую пару, позже - `upgraded`.
- **`extra_expired`**: устройство не помещается только потому, что доп. слот подписки не продлён или не оплачен (с оплаченным слотом оно бы поместилось). Активация - 409 (как `device_limit`), `/v1/search` и `/v1/torrent` - 403. Получают его только приложения с парой токенов (`"tokens": "pair"`, access-токен); старые токены и активация без пары по-прежнему получают `device_limit`, который старые приложения понимают. Телефон пишет «Доп. устройство не продлено - продлите его в боте».
- `/v1/search`, `/v1/torrent`, `/v1/me`, `/v1/link/clear` принимают и access-токен, и старый токен. Плохой access-токен - 401 (телефону: обновить токен); для старого токена всё как раньше (403 `expired` / `device_limit`).

### Телефон (PR-5)

- Активация шлёт `"tokens": "pair"`. На Android refresh-токен держит само приложение (`BillingTokens.kt`), **только** в Keystore (`js:billing.refresh`); страницы его не видят - активация и переход со старого токена отдают его приложению (`billingAdopt`). Если Keystore отказал в записи, токен нигде не сохраняется: живёт в памяти процесса, в журнал Android пишется строка без значения, старая запись в Keystore удаляется; после перезапуска сессия сбрасывается и экран кода пишет «Ключ подписки не сохранился на телефоне - введите код заново». Только браузерная сборка (без Keystore) держит refresh в `tsp.billingSession`. Access-токен и сроки - в `tsp.billingSession` (в резервную копию не попадает).
- Обновление пары: заранее, когда до конца access-токена меньше 2 ч (при старте, при возврате в приложение и раз в 30 мин), и по 401 `token_expired` / `bad_token` с одним повтором запроса. Одно обновление за раз на весь процесс (приложение, фоновая проверка, поисковый сервер для ТВ): кто пришёл во время обновления, ждёт и получает уже новый access-токен без второго запроса. Потерянный ответ (сеть, тайм-аут) - тот же refresh-токен ещё раз через 3 с, в пределах 60 с сервера. Ошибка сети никогда не отключает устройство; забывает токен только 401 `revoked` / `refresh_expired` / `bad_token` от сервера.
- Скрытые страницы (фоновая проверка, поисковый сервер для ТВ) обновляют access-токен через приложение (`billingRefresh` по мосту), поэтому поиск с ТВ работает, даже если приложение на телефоне не открывали больше суток. Переход со старого токена делает только страница приложения.
- 401 `revoked` / `refresh_expired` / `bad_token` на refresh (и `revoked` на любом запросе) - привязка забывается, на экране кода: «Устройство отключено - введите новый код».
- Старая установка: при первом запуске новой версии - один `POST /v1/token/upgrade` (с повтором через 3 с при потерянном ответе). Сеть / 5xx / 429 / 404 - остаётся старый токен, новая попытка через 5 мин; `upgraded` / `bad_token` / `revoked` - «Устройство отключено».

### Позже: `BILLING_LINK_CLEAR_REQUIRE_TOKEN=1`

Не включать сейчас. Шаг - после того как телефоны перешли на новые токены:

1. Проверить в админке («Устройства»), что строк со «старым токеном» с недавним `lastSeen` не осталось (или осталось ожидаемое число).
2. Помнить: телефон, привязанный к Telegram **без кода**, токена не имеет и после включения не сможет отвязать Telegram из приложения (только в боте).
3. На сервере (каталог стека из `ops/vps/README.md`): бэкап `.env` (`cp -p .env .env.bak-$(date +%Y%m%d-%H%M%S)`), дописать `BILLING_LINK_CLEAR_REQUIRE_TOKEN=1`, `docker compose up -d billing`.
4. Проверить: `POST /v1/link/clear` без `Authorization` → 401 `token_required`; из приложения «Отвязать» Telegram работает.
5. Откат: убрать строку из `.env` (или `=0`) и `docker compose up -d billing`.

## Хранилище: Postgres

- Биллинг работает только на Postgres 17: `BILLING_DATABASE_URL=postgres://…`. Без строки подключения процесс не стартует (код 1). `BILLING_STORE` можно не задавать; `BILLING_STORE=sqlite` (или любое значение, кроме `postgres`) - ошибка при старте, чтобы старый `.env` не запустил биллинг на пустой базе. Путь SQLite удалён после переключения 19.10.2026.
- Состояние в нормализованных таблицах (`src/db/pg/`): схема создаётся миграциями при старте (`schema_migrations`), запись - одна транзакция под advisory-блокировкой, пишутся только изменившиеся строки, журналы (аудит, попытки входа, проблемы ЮMoney, сообщения поддержки) не удаляются, а помечаются `live = false`. Строка подключения не логируется; при ошибке подключения в stderr только код и текст ошибки.
- Старый `data/billing/billing.db` остаётся на диске как архив (биллинг его не читает и не пишет). Прочитать его в пустую базу Postgres можно инструментом `tools/migrateToPostgres.mjs` (есть в образе): `BILLING_DATABASE_URL=… node tools/migrateToPostgres.mjs --from /data/billing.db` - сухой прогон (всё переносится и сверяется в транзакции, затем откат); `--apply` - запись, только в пустую базу и только если сверка прошла. Отчёт (`--report файл`) - числа, id и короткие хэши, без значений настроек и токенов.
- Тесты биллинга идут на Postgres: `BILLING_TEST_DATABASE_URL=postgres://…` (в CI - сервис postgres:17), каждый тест в своей схеме.
- Сроки хранения журналов на Postgres: аудит и проблемы ЮMoney - 1 год, попытки входа - 90 дней (раз в сутки).
- Сервис postgres в compose NUC, бэкапы и переключение - ранбук `docs/billing/postgres-cutover.md`.
- `BILLING_READONLY=1` - окно переключения: чтение (поиск, `/v1/me`) работает, любая запись → 503 `read_only` (ЮMoney - `503 read only`, повторит уведомление), бот, напоминания и чистка журналов не запускаются, `/health` → `"readOnly":true`.
- Бэкапы Postgres: при `BILLING_PG_BACKUP_DIR` + `BILLING_DATABASE_URL` биллинг сам делает `pg_dump -Fc` раз в `backupEveryHours` (админка, 1-168 ч, по умолчанию 24) и хранит `backupKeepDays` (1-365, по умолчанию 30; последний не удаляется). Файлы `billing-YYYYMMDD-HHMMSS.dump`, права 600. `/health` → `pgBackupOk`, `pgBackupAgoSec`; устаревший бэкап - предупреждение на главной админки; устаревший или неудачный бэкап - одно сообщение админам в Telegram (и одно, когда снова в порядке; выключается вместе с уведомлениями админам).

## Бот: тайм-ауты и `/health`

- Запросы к Telegram Bot API с жёстким сроком (`telegramCall`): `getUpdates` - 40 с (`TG_POLL_TIMEOUT_MS`, long-poll 25 с), `sendMessage` и `getChat` - 15 с (`TG_SEND_TIMEOUT_MS`). Зависшее соединение больше не останавливает цикл бота.
- Неудачный `getUpdates` (тайм-аут, сеть, HTTP-ошибка) пишет в stderr строку `telegram getUpdates failed: <вид>` не чаще раза в минуту, с числом пропущенных с прошлой строки. URL и текст ошибки в строку не попадают (в них токен бота).
- `GET /health` → `{"ok": true, "botPollEnabled": true, "botPollOkAgoSec": 12}`: секунды с последнего успешного `getUpdates`; `null`, пока его не было или опрос выключен. Без секретов - мониторинг проверяет бота, не читая токен.

## Мониторинг

Вкладка **Мониторинг** в панели (вход только через Telegram, как и вся панель): таблица проверок с зелёным или красным статусом, временем ответа, полосой за 7 дней (по часам) и процентом успешных проверок. Кнопка «Проверить сейчас» запускает проверку в фоне (весь прогон - до нескольких минут), вкладка обновляется каждые 3 с, пока он идёт. Код: `src/monitor.mjs` (расписание, история, алерты), `src/monitorChecks.mjs` (проверки), `src/monitorHttp.mjs` (запрос напрямую или через прокси).

Проверки:

| Группа | Что | Красный, если |
| --- | --- | --- |
| Инфраструктура | Postgres `SELECT 1` | нет ответа |
| | Бэкап Postgres (та же логика, что `pgBackupOk` в `/health`) | дамп устарел или последний `pg_dump` упал |
| | Опрос бота (`botPollOkAgoSec`) | последний успешный `getUpdates` больше 180 с назад |
| | Диск `/data` и каталог бэкапов (`statfs`) | свободно меньше 10% или меньше 2 ГБ |
| | Cloudflare trace через `http://warp:1080` | нет `warp=on` |
| Сервисы | Jackett, JacRed (Torznab caps), TorrServer (`/echo`) во внутренней сети | нет ответа или HTTP-ошибка |
| Сайты | `omp-player.online` 200, `billing.omp-player.online/admin/` 200, `jackett.` и `jacred.omp-player.online` 401 (по коду и заголовкам, тело страницы не читается) | другой код или нет ответа |
| Контейнеры | каждый контейнер проекта `omp-vps`: статус, health, перезапуски, память | не `running`, `unhealthy`, OOM, `RestartCount` вырос с прошлой проверки, память больше 90% лимита |
| Трекеры Jackett | каждый трекер из `t=indexers&configured=true`: поиск через Jackett, сайт трекера напрямую и через WARP | поиск не вернул Torznab; сайт: нет ответа, 5xx или редирект на страницу блокировки |
| JacRed | свежесть базы (`/lastupdatedb`, не старше 6 ч), поиск, `sync.jacred.stream` и сайт каждого трекера из `/api/v1.0/trackers` напрямую и через WARP | так же |

Список трекеров читается с ключом API из `.env` (Jackett: Torznab `t=indexers`, JacRed: `/api/v1.0/trackers`). Ключи уходят только в запросы к этим контейнерам во внутренней сети; в базе, ответе панели, логе и алертах их нет: текст ошибки чистится от query-строк, `key=...` и самих ключей (`cleanDetail`). JacRed берёт базу с `sync.jacred.stream` и сам на трекеры не ходит, поэтому для его трекеров видна только доступность сайта. Адреса сайтов JacRed - значения по умолчанию jacred-fdb (`JACRED_TRACKER_SITES`).

Сайт трекера считается доступным при любом HTTP-ответе ниже 500. Страница с капчей или проверкой на робота - жёлтый статус «Просит код»: человек сайт откроет, поэтому алерта нет и в красные он не считается. Признаки: заголовок `cf-mitigated: challenge`, 403/503 от Cloudflare, 403/429/503 от DDoS-Guard, а для ответов 200/403/429/503 ещё и начало страницы (до 16 КБ и не дольше 3 с, медленное тело не превращается в таймаут): заголовок страницы с капчей, скрипт проверки Cloudflare, на 403/429/503 и слова вроде «captcha», «введите код». Если трекер был красным с алертом и стал жёлтым, алерт закрывается сообщением «починилось» с пометкой «сайт отвечает, но просит код». Жёлтое видно в фильтре «Просит код», при сортировке по статусу оно между красным и зелёным, а в свёрнутой группе пишется «12/12, 1 жёлтая». Красный «напрямую» при зелёном «через WARP» - трекер закрыт у провайдера; это видно в таблице, но алерта нет. Алерт по трекеру: не работает поиск через Jackett (путь пользователей; Jackett сам ходит через WARP и FlareSolverr) или сайт не открывается ни напрямую, ни через WARP.

Контейнеры читаются через `omp-docker-proxy` (`tecnativa/docker-socket-proxy`, `CONTAINERS=1`, `POST=0`, только внутренняя сеть `dockerapi`). Из ответа `inspect` берутся только `State`, `RestartCount` и память; переменные окружения контейнеров не сохраняются и не показываются. Перезапустить или остановить контейнер из панели нельзя. Ограничение прокси: `CONTAINERS=1` пропускает и другие GET под `/containers` (логи, файлы контейнера через `archive` и `export`); billing их не вызывает, а до прокси дотягивается только billing по сети `dockerapi`.

Во вкладке сначала красное: группы с ошибками сверху и раскрыты, полностью зелёные свёрнуты в строку «Контейнеры 12/12» (раскрываются кликом). Фильтр «Все / Только ошибки / Без алерта / Просит код» («Без алерта» - красное, по которому алерт не уходит; «Просит код» - жёлтые сайты с капчей), поиск по названию, адресу и тексту ошибки, сортировка по статусу, названию, времени ответа и времени проверки; выбор хранится в localStorage браузера. «Перепроверить все ошибки» запускает заново только красные проверки (остальные сохраняют последний результат, в историю идут только перепроверенные, следующая плановая проверка не сдвигается). У красной строки есть своя кнопка «Перепроверить»: запускает только эту проверку (у трекера только его красные проверки) с тем же повтором через 30 с, алертами и историей; пока идёт другая проверка, кнопка недоступна, а сервер такой запрос отклоняет. Во время проверки вверху «Проверка идёт: N из M, начата ЧЧ:ММ:СС МСК» с полосой, у строк состояние «в очереди / проверяется / ждёт повтора / готово»; после конца строка «Готово»: сколько проверено, сколько ошибок, сколько повторено, сколько заняло.

Расписание: по умолчанию раз в 15 минут, интервал (5-1440 минут) меняется во вкладке и применяется без перезапуска. Расписание работает только там, где `BILLING_BOT_POLL` включён и нет `BILLING_READONLY`, чтобы второй экземпляр не дублировал алерты; `BILLING_MONITOR=0` выключает его (кнопка остаётся). Упавшая проверка перед алертом повторяется через 30 с. Алерт уходит ботом (только `sendMessage`) в чат `BILLING_MONITOR_CHAT_ID` (по умолчанию 536445442) один раз на проблему, пока она длится, повторов нет; когда проверка снова зелёная, приходит «починилось». Не ушедшее сообщение отправляется на следующей проверке; длинный список уходит несколькими сообщениями. Если Postgres недоступен, мониторинг работает на последних прочитанных настройках и состоянии (в памяти), алерт про Postgres уходит, а история этой проверки не сохраняется. Если не прочитан список (контейнеры, трекеры Jackett или JacRed), он перечитывается при повторе через 30 с, а алерты по его строкам не закрываются, пока список не прочитан. История хранится 7 дней (таблицы `monitor_runs` и `monitor_results`, миграция `002_monitor`); состояние алертов, интервал и счётчики перезапусков - в `kv` (`monitor_alerts`, `monitor_config`, `monitor_restarts`).

## Продление, льготный период, доп. устройства, напоминания

- **Льготный период.** После `paidUntil` доступ (поиск, `/v1/torrent`, активация кода) сохраняется ещё `graceDays` дней (по умолчанию 3, настройка «Льготный период, дней» во вкладке **Настройки**, 0-30). Считается только по часам сервера. `GET /v1/me` в это время отвечает `active: true, inGrace: true, accessUntil`, бот пишет «Подписка закончилась … Льготный период: поиск работает до … МСК», в панели статус «льготный период». Оплата продления в льготный период продлевает от старого `paidUntil` (льготные дни не бесплатные), после него - от момента оплаты. Подарочные дни (промокод, «Выдать дни») по-прежнему считаются от `max(paidUntil, сейчас)`.
- **Доп. устройство - помесячно.** Покупка `dev` (50 ₽ по умолчанию) добавляет слот `extraSlots` до `extraUntil` = текущий `paidUntil`. Продление стоит `priceRub + extraDeviceRub × действующие слоты`; бот показывает разбивку и вторую ссылку «Без доп. устройств». Оплаченное продление переносит слоты на новый `paidUntil`. Не продлённый слот работает до `extraUntil` + льготный период, потом лимит падает: доступ теряет последнее привязанное устройство сверх лимита (по `boundAt`). Привязка и сессия не удаляются: `/v1/me` отвечает `active: false, overLimit: true`, поиск - `403 {"error":"device_limit"}`, после покупки слота устройство снова работает без нового кода. Подарочные дни переносят и действующие слоты. После льготного периода «Продлить» (и «Подписка» для закончившейся подписки) по-прежнему предлагает 150 + 50 × слоты, которые закончились вместе с подпиской, с разбивкой и второй ссылкой «Без доп. устройств». Полная оплата возвращает слоты на новый период, привязанные устройства снова работают без нового кода. После продления без доп. устройств слот больше не предлагается, новый покупается через «Код».
- **Миграция.** Снимок без `meta.extraMonthly` при первом чтении переносит всё, что выше `DEVICE_BASE` в `deviceLimit`, в `extraSlots` с `extraUntil = paidUntil` (купленные навсегда слоты действуют до конца текущей оплаты, дальше продлеваются вместе с подпиской). Срабатывает один раз.
- **Напоминания в Telegram**: за 3 дня, за день и в день окончания, по московскому календарю, с 10:00 МСК до конца того же дня (пропущенный день не догоняется). Каждое уходит один раз на дату окончания: отметка `reminders` хранится в подписке и ставится до отправки, после продления цикл начинается заново. Если Telegram не принял сообщение, повтор через 10 минут, не больше 3 попыток. Напоминание, время которого наступило раньше покупки или продления (например, промокод на 1 день), не отправляется. Когда льготный период закончился, один раз приходит «Льготный период закончился - поиск в OMP отключён» с ценой продления и разбивкой по доп. устройствам и кнопкой «Продлить»: с 10:00 МСК того же московского дня или сразу, если период закончился позже 10:00, до конца этого дня (поздний конец - ещё час). Отметка `end` в том же `reminders`, после продления сбрасывается. Таймер работает внутри процесса (каждые 10 минут) и только там, где `BILLING_BOT_POLL` включён, поэтому вторая копия сервера напоминаний не дублирует.
